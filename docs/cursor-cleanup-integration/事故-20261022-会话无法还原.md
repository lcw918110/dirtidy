# 事故：清理后 Cursor 会话无法还原（2026-10-22）

> 给 `dirtidy cursor-cleanup` 开发会话的**硬约束输入**。
> 办公仓参考脚本已经犯过；dirtidy **不能再犯**。
> 当前权威行为仍以 `docs/02` FR-12、`docs/09` §2.12 为准；本文件是新增事故，
> 其中尚未写进 FR-12 的条款，开发会话必须补进需求/设计/测试后再改代码。

---

## 1. 用户看到的现象

Cursor 弹出（无法在原对话继续）：

```text
This conversation's data is missing and can't be restored. Start a new chat to continue.
(3 missing blobs: 0203ebc74590, 00a8f0e42850, 0120dc7d37b2)
Request ID: 4883c320-56a1-4414-8ceb-4c797022bc33
```

- 坏的会话：`c86e8b80-a181-4c6e-ab44-575551342b16`（ADMIN-BUS 工作区，10/16 起的长对话）
- 触发：2026-10-22 16:13 在该会话提交 `/审视`
- 结果：UI 判死，只能新开对话

## 2. 时间线（与清理程序的关系）

| 时间 | 发生了什么 |
|------|------------|
| 10/09–12 | 办公仓脚本清 `state.vscdb`：默认无参数即清理；当时 >90 天会话为 0 |
| **10/21** | 办公仓脚本加 `--blob-only`，**Cursor 仍在运行时**在线 DELETE 无引用 `agentKv:blob`。删了约 **5413** 个 blob 后 Cursor 报 `storage file corrupted/moved/permission`，脚本被紧急杀掉 |
| 10/21 | dirtidy 已集成 `cursor-cleanup`：默认干跑、Cursor 在跑拒绝、引用扫全部非 blob 前缀 |
| **10/22** | 上述长会话无法还原，缺 3 个 **12 位 hex** blob |

## 3. 已核实的事实（只写查过的）

真机只读查询（Cursor 开着，`mode=ro`）：

| 项 | 结果 |
|----|------|
| `state.vscdb` 体积 | 约 **75.9 GB** |
| `agentKv:blob:` 行数 | 约 **71.9 万**；key 形态是 **64 位 hex**，例如 `agentKv:blob:000033ae5049a8335a…` |
| 缺失的 3 个 ID | **12 位 hex**，不是 64 位 |
| 这 3 个 ID 是否作为 key 存在 | **否**（`LIKE %id%`、`agentKv:blob:<id>%` 前缀均为 0） |
| 是否出现在该会话 `composerData` / 1630 条气泡 value | **否** |
| Chromium `blob_storage` | 只有 1 个 UUID 目录，文件名不含这 3 个 ID |
| 该会话是否被清掉头 | **否**：`composerHeaders` 仍在，`composerData` 112 KB，气泡 1630 条，recency=当天 16:13 |

本地逐字稿仍在（清理程序没碰它，UI 却已经不能还原）：

`~/.cursor/projects/…ADMIN-BUS/agent-transcripts/c86e8b80-…/c86e8b80-….jsonl`

**不能写成已证明的**（10/22 原判断，已被后续取证修正，见 §3.1）：这 3 个 12 位 ID 就是 10/21 删掉的那 5413 个 `agentKv:blob` 之一。
key 空间对不上。能写成已证明的是下面两条：

1. **在线改 `state.vscdb` 会让 Cursor 报库损坏并拒绝启动**（10/21 已复现）。
2. **会话还原依赖另一套 blob 标识（12 位 hex）**；只按 `cursorDiskKV` 里 64 位哈希做「无引用即可删」，**覆盖不了这套还原协议**。删完之后，UI 仍可能报 missing blobs，且这 3 个 ID 在本机 KV 里已经找不到，**UI 无法还原**。

### 3.1 取证修正（2026-10-22 晚，dirtidy 开发会话补充）

用 `state.vscdb.pre-cleanup`（10/21 清理前冷备份）对照当前库，**修正**本文初版的
「两套无关标识」判断：

- 三个 12 位 ID 恰好是三个被删 64 位 blob key 的**前缀**：
  `0203ebc74590` → `agentKv:blob:0203ebc74590b84d…`（另两个同理，GLOB 精确命中）；
- 三个 blob 在 pre-cleanup 库**存在**、在当前库**不存在** → 确系 10/21 清理删除；
- **blob key = sha256(value)**（三例全部验证）——内容寻址，与 toolCallId 无哈希关系；
- blob value 是 tool-result JSON：`{"role":"tool","content":[{"type":"tool-result","toolCallId":"call_…","toolName":"Read",…}]}`；
- 会话气泡 key 形态 `bubbleId:<cid>:<uuid>/t:call_<toolCallId>` 引用工具结果；
  三个 toolCallId 中两个的 `/t:` 气泡仍在库里，**第三个已不在**（子代理/云端需求，
  本地不可枚举）；
- **toolCallId 只出现在气泡 key 里，不出现在任何 value 里**（气泡 value 是标准
  `_v:3` JSON，不含 64 位哈希；blob value 也不含）。

**根因定论**：现有孤儿判定（扫全部 value 找 64 位哈希）对 tool-result blob
**结构性失明**——引用协议在 key 里，不在 value 里。这不是「扫得不够全」的问题，
任何 value 扫描改进都覆盖不了。据此 dirtidy 的修复是：**默认不删 blob** +
显式高危开关（`--delete-blobs`）+ 逐字确认（`--blob-confirm`）+ toolCallId 守卫
（存在 `/t:` 气泡时 tool-result 形态孤儿一律保留）。

## 4. 分层原因（给开发用）

### 4.1 直接原因（用户感知）

Composer 还原会话时要取 3 个 blob，本地/云端都没有 → 整段对话判死。

### 4.2 清理程序已经犯过的错

1. **Cursor 还在跑就写库**（`--blob-only` 在线 DELETE）。抢 WAL 锁 → Cursor 报 `storage corrupted`。批间 sleep / 锁退避 **不能**当成「可以在线清」的承诺。
2. **引用扫描范围过窄**（办公仓参考实现只扫 `bubbleId` / `checkpointId` / `composerData`）。dirtidy 已用真机对照证明：漏扫 `ofsContent:` 等前缀会把**活 blob** 判成孤儿（当时差 1 个）。这条已经修，必须保持。
3. **把「KV 里扫不到 64 位引用」当成「删了不影响会话」**。10/22 事故说明：还原用的是 **12 位 blob ID**，不在 `agentKv:blob:<64hex>` 这套 key 里。现有孤儿判定即使扫全前缀，也**证明不了**会话还原仍然完好。

### 4.3 两套 blob，禁止混为一谈（10/22 取证修正后的准确表述）

| | `agentKv:blob`（清理器认识的） | 会话还原 missing blobs（本次事故） |
|--|--|--|
| ID 长度 | 64 位 hex（= sha256(value)） | UI 显示 **12 位 hex = 64 位 key 的前缀**（取证修正） |
| 存放 | `state.vscdb` → `cursorDiskKV` | 同一批 blob；引用协议在气泡 key `…/t:call_<toolCallId>` 里，**不在任何 value 里**（第三个的气泡已不在本地库，属子代理/云端需求，不可本地枚举） |
| 误删后果 | 附件/快照丢、体积下来 | **整条对话 UI 无法继续** |

## 5. 硬约束（不能再犯）

开发 `dirtidy cursor-cleanup` 时按条落地到需求、实现、测试。缺测试的条款不算修完。

1. **Cursor 在跑 → 拒绝任何写**（含所谓「在线 blob-only」）。判断不了是否在跑 → 也按在跑。禁止再提供「Cursor 可继续工作」的删库模式。
2. **默认干跑**。必须显式 `--apply` 才改库。禁止办公仓那种「无参数即清理」。
3. **引用扫描必须覆盖 `cursorDiskKV` 全部非 blob 前缀**（已有用例，不许退回三前缀）。
4. **禁止把 64 位孤儿名单当成会话安全的充分条件。** 在未证明 12 位还原 blob 的引用关系之前：
   - 要么 **默认不删 `agentKv:blob`**（`--no-blob` 为默认，删 blob 要另开更危险的开关）；
   - 要么删 blob 之前增加**可证伪的会话还原守卫**（例如：近期 `composerHeaders` 对应会话，还原所需 blob 仍在；或明确文档声明「删 blob 可能导致旧会话 UI 无法打开，逐字稿以 `agent-transcripts/*.jsonl` 为准」并要用户二次确认）。
   - **不允许**只靠「value 里没有这个 64 位哈希」就删。

   > **落地状态（2026-10-22）**：dirtidy 已按本条修复——默认不删 blob（`--delete-blobs`
   > 显式开关 + `--blob-confirm` 逐字确认），且判定内置 toolCallId 守卫（取证证明
   > 引用在气泡 key 协议里、不在任何 value 里，见 §3.1）。8 条事故回归用例已入库。
5. **清理范围只许是** `state.vscdb`（及其 wal/shm、VACUUM 产物、自己写的备份/审计）。**禁止碰**：
   - `~/.cursor/projects/*/agent-transcripts/`
   - `~/.cursor/chats/`
   - Chromium `blob_storage` / IndexedDB
   - `ItemTable`（设置）
6. **按 `recency` 保留的近 N 天会话**：header、`composerData`、气泡、checkpoint **全部保留**。不得因「孤儿扫描」删掉仍在 header 里的近 N 天会话正文。
7. **WAL checkpoint / VACUUM 前必须释放本进程全部游标与连接**（办公仓曾报 `database table is locked`）。checkpoint 用独立连接 + `busy_timeout`。
8. 出问题后的诚实口径：UI 会话丢了但 jsonl 还在，就说「Cursor 窗口还原不了，逐字稿还在，请新开对话」；**不要**声称能把 12 位 blob 从备份里对号插回去，除非真的找到了对应存储并验证可还原。

## 6. 建议的测试（至少）

- Cursor 进程存在时 `--apply` 退出码非 0，库字节不变。
- 无 `ps` / 取进程失败时同样拒绝 `--apply`。
- 构造 `ofsContent:<id>` value 含 64 位哈希时，该 blob **不得**进入孤儿名单。
- 构造仅 12 位 ID、没有 64 位哈希的「还原引用」时，**不得**把对应数据当孤儿删掉（若实现选「默认不删 blob」，用默认路径断言 blob 行数不变即可）。
- 清理后 `ItemTable` 行数不变；`agent-transcripts` 目录不被访问。
- 无 `--apply` 时文件 mtime/size 不变。

## 7. 给用户的可执行建议（产品文案可引用）

真正缩盘仍须 **完全退出 Cursor** 后 `--apply`。  
若只想保会话、接受库继续大：干跑即可，不要删 blob。  
某条对话若已报 missing blobs：**不要再往那条里发消息**；到原工作区新开对话；需要旧结论时读对应 jsonl。
