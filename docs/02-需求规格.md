# dirtidy — 需求规格

## 1. 功能需求

### FR-1 扫描

- 用户指定根目录（绝对或相对路径），递归枚举文件与目录。
- 记录：相对路径、大小、mtime、是否目录、扩展名；可选内容 hash（可 `--quick` 跳过深 hash）。
- 权限不足：记入失败列表，不中止整次运行。

### FR-2 规则引擎

- 从 YAML 规则包加载规则（内置 `default`、`server_workspace` 等）。
- 每条规则含：`id`、`action`（`auto_quarantine` | `candidate_only`）、匹配条件、说明。
- 高置信匹配项执行隔离；候选写入 `candidates.json`。
- `protect` 保护清单优先级最高：命中即永不自动隔离，也不进入候选。判定是**双向**的：
  - 目录命中保护 ⇒ 其整棵子树受保护（`.git` 被保护 ⇒ `.git/objects/…` 不可被搬走）；
  - 一个命中自动隔离的目录，若子树内含受保护路径 ⇒ **整条命中被拦下**并记入 `protection.json`
    （`blocked_at=protected_descendant`）。否则保护会被「搬走它的父目录」这条捷径绕开——
    `node_modules` 命中 dep 规则时，`node_modules/.env`、`node_modules/id_rsa` 就会被一并端走。

### FR-3 隔离区

- 默认将目标移入隔离目录（不直接抹盘），记录原路径、隔离路径、规则 id、时间、大小、hash（若有）。
- 支持按 run / 条目还原；彻底清除为独立命令且需显式确认。

### FR-4 解压残留与压缩包内容

- 对 zip/tar/tar.gz 等：枚举成员并计算成员内容 hash，与磁盘文件 hash 对照；达阈值才标「压缩包可清」候选。
- 禁止仅凭压缩包文件名或同名目录判定。
- 旁路压缩包是否像安装分发：基于成员结构/类型探测后标候选，默认不自动隔离。

### FR-5 重复文件

- 同内容 hash 分组；默认不自动隔离。
- 用户在 Web 或 CLI 中为每组指定保留项，其余可标记隔离。

### FR-6 审计

- 每次 run 产出：`inventory.json`、`candidates.json`、`quarantine_manifest.json`、`audit.md` 等。
- 审计含删除/隔离内容的基本信息，可回放。

### FR-7 模型分析（Step2）

- Provider：`openai_compatible`、`ollama`（可配）。
- 输入默认安全摘要（路径可脱敏、ext、size、mtime、类型、文本抽样上限、hash 前缀）；密钥类/二进制不抽样。
- 外发正文默认关；完整正文有两条显式开启路径——`provider=ollama` 且 `allow_ollama_full_content: true`（本机），或 `provider=openai_compatible` 且 `allow_external_content: true`（外发到外部端点，需用户显式承担）。
- 输出维度见架构文档；仅建议，不自动执行。

### FR-8 决策与执行

- Web/CLI 写入 `decisions.json`（keep / quarantine / archive + 目标相对路径）。
- `apply-decisions` 按决策执行移动或隔离。
- **隔离前同样复核保护清单**：保护的最高优先级不因走规则路径还是决策路径而不同；
  被拦下的记入 `skipped` 并写入 `protection.json`。复核覆盖「目录命中带走受保护后代」这一情形
  （见 FR-2），因此人工把整个目录标成 quarantine 也不能绕开保护。
  `archive` 不拦——它是显式指定目标的归类，文件仍在根内可找回，与「清理」语义不冲突。
- 规则自动隔离（`apply-rules`）可在执行前人工保留指定项（CLI `--keep` / Web 勾选）；
  保留项本轮不动，并登记进 `protection.json`（`protect_rule_id=user_kept`）以便审计追溯——
  「用户不想动它」与「内置清单保护它」在结果上是同一件事。
- 隔离计划（`plan_quarantine`）是**预览与实跑的唯一来源**：`--dry-run` 报出的「会搬哪些、拦下哪些」
  必须与真实执行逐条一致；同一目录与其内文件同时命中时只保留父目录一条，避免产生无法还原的清单记录。

### FR-9 界面

- CLI：scan、explain、apply-rules、restore、purge、analyze、apply-decisions、save-decisions、serve。
- 破坏性操作均提供 `--dry-run` 预览：`scan` / `apply-rules` / `apply-decisions` 可先看「会动哪些、哪些被保护拦下」再决定执行。
- `explain <相对路径>`：逐条摊开规则匹配、`when` 条件判定与保护判定（含规则来源），回答「为什么动/不动它」。
- 本地 Web：加载 run；展示**待自动隔离**（可勾选保留并直接执行自动隔离）、候选与 AI 建议、重复组、
  **受保护清单**、**已隔离清单**；勾选决策并触发执行；对任一路径可就地查看「为什么？」
  （与 CLI `explain` 同一份解释）。
  待自动隔离摆在候选之前，因为它是「不误删」的终审入口——看不到规则打算动什么，终审就无从谈起。

## 2. 非功能需求

| 编号 | 要求 |
|------|------|
| NFR-1 | 支持 macOS、Linux、Windows（路径与换行差异由标准库处理） |
| NFR-2 | 无模型时 Step1 完整可用 |
| NFR-3 | 默认不静默彻底删除 |
| NFR-4 | 超大目录可用 quick 模式降低 hash 成本 |
| NFR-5 | 配置与密钥不入库；示例用 `*.example.yaml` |
| NFR-6 | 扫描常驻内存与文件数线性且系数固定；不构造与 inventory 等长的第二份结构 |
| NFR-7 | 扫描可中断续跑：已算过的内容 hash 不重复计算（SQLite 缓存） |
| NFR-8 | 进度回调按 1% 节流，不因反馈本身拖慢扫描 |
| NFR-9 | 归档解析、重复分组、模型外发均有硬上限，单个异常输入不能拖垮整次运行 |
| NFR-10 | 产物写盘流式化，峰值内存不随产物条数增长 |

规模目标与实测数据见 `docs/07-规模与性能.md`（500 万条 / T 级数据，内存上限 1.5 GB）。

## 3. 验收标准（MVP）

1. 夹具目录上：`scan` + `apply-rules` 能隔离 `node_modules`/`__pycache__`/空目录等，并生成审计。
2. 构造「压缩包内文件 hash = 磁盘文件」时，压缩包进入候选而非仅靠文件名。
3. 重复组出现在候选中，未人工决策前不自动隔离组内全部文件。
4. 配置 mock/本地 provider 时 `analyze` 写出 `ai_suggestions.json`。
5. Web 能加载 run 并保存 decisions；`apply-decisions` 生效。
6. `quarantine-restore` 能还原已隔离条目。
7. 审阅页能看到待自动隔离项与受保护清单；勾选保留后执行自动隔离，保留项留在原地且记入 `protection.json`。
8. `node_modules/.env` 这类「受保护文件躺在将被隔离的目录里」的情形，目录被整体拦下，密钥文件原地不动，
   且 `protection.json` 留有 `blocked_at=protected_descendant` 的记录。
