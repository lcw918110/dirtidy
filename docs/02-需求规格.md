# dirtidy — 需求规格

本文定义功能、安全边界与验收要求，不作操作教程。日常使用见 [使用手册](09-功能与使用汇总.md)；实现契约见 [架构设计](03-架构设计.md)。正文为当前要求，末尾修订记录仅供追溯；尚未覆盖的边界见 [待办台账](06-已知缺口与后续.md#待办台账)。

## 1. 功能需求

### FR-1 扫描

- 用户指定根目录（绝对或相对路径），递归枚举文件与目录。
- 记录：相对路径、大小、mtime、是否目录；可选内容 hash（`--quick` 完全跳过）。
  扩展名不单独存字段——它可由路径现算（`suffix_of(path)`），每条常驻一个后缀字符串在 500 万条下要多花约 250 MB（见 `docs/07`）。
- 内容 hash **按需计算**：只对「size 出现 ≥2 次」与「size 命中某个归档成员」的文件算 sha256。
  重复组与归档残留对照都要求同 size（同内容必然同字节数），因此没被算到的文件既不可能重复、
  也不可能与归档成员相同——结论与全量算一致，代价却小一个量级（见 `docs/07` §3.2）。
- 权限不足：记入失败列表，不中止整次运行。

### FR-2 规则引擎

- 从 YAML 规则包加载规则（内置 `default`、`server_workspace` 等）。
- 每条规则含：`id`、`action`（`auto_quarantine` | `candidate_only`）、匹配条件、说明。
- 高置信匹配项执行隔离；候选写入 `candidates.json`。
- `protect` 保护清单优先级最高：命中即永不自动隔离，也不进入候选。判定是**双向**的：
  - 目录命中保护 ⇒ 其整棵子树受保护（`.git` 被保护 ⇒ `.git/objects/…` 不可被搬走）；
  - 一个命中自动隔离的目录，若子树内含受保护路径 ⇒ **整条命中被拦下**并记入 `protection.json`
    （`blocked_at=protected_descendant`）。否则保护会被「搬走它的父目录」这条捷径绕开——
    `node_modules` 命中 dep 规则时，`node_modules/.env`、`node_modules/id_rsa` 就会被一并端走。
- 这份判定必须覆盖**所有会搬文件的执行路径**（`apply-rules`、`apply-decisions`、`scan --apply`），
  且共用同一份实现。三条路径各写一遍保护检查迟早会漂移，而漂移的那一条就是绕开保护的缝。

### FR-3 隔离区

- 默认将目标移入隔离目录（不直接抹盘），记录原路径、隔离路径、规则 id、时间、大小、hash（若有）。
- 支持按 run / 条目还原；彻底清除为独立命令且需显式确认。

### FR-4 解压残留与压缩包内容

- 对 zip/tar/tar.gz 等：枚举成员并计算成员内容 hash，与磁盘文件 hash 对照；达阈值才标「压缩包可清」候选。
  成员解析先于 hash 阶段（`probe_archives`），因为成员的解压后字节数决定磁盘上哪些文件需要算 hash。
- 禁止仅凭压缩包文件名或同名目录判定。
- 旁路压缩包是否像安装分发：基于成员结构/类型探测后标候选，默认不自动隔离。

### FR-5 重复文件

- 同内容 hash 分组；默认不自动隔离。
- 用户在 Web 或 CLI 中为每组指定保留项，其余可标记隔离。

### FR-6 审计

- 每次 run 产出：`inventory.json`、`candidates.json`、`quarantine_manifest.json`、`audit.md` 等。
- 审计含删除/隔离内容的基本信息，可回放。

### FR-7 模型分析（Step2）

- Provider：`openai_compatible`、`ollama`（可配）。
- 输入默认安全摘要（路径可脱敏、ext、size、mtime、类型、文本抽样上限、hash 前缀）；密钥类/二进制不抽样。
- 外发正文默认关；完整正文有两条显式开启路径——`provider=ollama` 且 `allow_ollama_full_content: true`（本机），或 `provider=openai_compatible` 且 `allow_external_content: true`（外发到外部端点，需用户显式承担）。
- 输出维度见架构文档；仅建议，不自动执行。

### FR-8 决策与执行

- Web/CLI 写入 `decisions.json`（keep / quarantine / archive + 目标相对路径）。
- `apply-decisions` 按决策执行移动或隔离。
- **隔离前同样复核保护清单**：保护的最高优先级不因走规则路径还是决策路径而不同；
  被拦下的记入 `skipped` 并写入 `protection.json`。复核覆盖「目录命中带走受保护后代」这一情形
  （见 FR-2），因此人工把整个目录标成 quarantine 也不能绕开保护。
  `archive` 不拦——它是显式指定目标的归类，文件仍在根内可找回，与「清理」语义不冲突。
- 复核由**同一份保护判定器**提供，`apply-rules`、`apply-decisions`、`scan --apply` 三条路径都走它；
  判定器的参数是必填的，调用方漏传会直接报错而不是静默放行（见 FR-2）。
- 规则自动隔离（`apply-rules`）可在执行前人工保留指定项（CLI `--keep` / Web 勾选）；
  保留项本轮不动，并登记进 `protection.json`（`protect_rule_id=user_kept`）以便审计追溯——
  「用户不想动它」与「内置清单保护它」在结果上是同一件事。
- 隔离计划（`plan_quarantine`）是**预览与实跑的唯一来源**：`--dry-run` 报出的「会搬哪些、拦下哪些」
  必须与真实执行逐条一致；同一目录与其内文件同时命中时只保留父目录一条，避免产生无法还原的清单记录。

### FR-9 界面

- CLI：start、scan、explain、apply-rules、quarantine-restore、purge-quarantine、analyze、apply-decisions、save-decisions、serve、desktop、watch、cursor-cleanup。
  `start` 是**最短路径**：必要时先扫描，然后起服务并打开浏览器——给「不想记命令」的人用；
  其余子命令都是它的可拆解步骤，需要脚本化时再单独用。
- **首屏必须给出动作，而不是只陈列数字。** 概览页第一眼要回答「现在该做什么」：
  一句话结论 + 一个可点的按钮 + 四步进度指示。高级选项（规则包、并行线程数、额外保护路径）
  与长流程说明**默认折叠**，不挡首屏——它们是给已经懂流程的人用的。
- **模型建议不得自动成为决策。** 候选表每行默认「保留不动」；模型建议只显示在「建议」列，
  要采纳得点「采纳全部建议」——且只填用户**尚未表态**的行，不覆盖手动修改。
  由此推出一条通用约束：**界面上「看起来已经生效」的东西，必须真的已经生效**。
  预填只写 DOM 不写状态、用户照着预填内容点执行却什么都不发生，是最隐蔽的一类欺骗。
- **执行类按钮必须在独立「执行」页紧挨它作用的清单**，并报出实际可执行条数与去向（隔离可还原；直删不可还原）后再确认。
  审阅页有两张表、两条执行路径（规则隔离 / 候选决策），按钮错位会让用户点到另一条路径上——
  那条路径根本不读他刚设的下拉。一条可执行决策都没有时要明说，不能静默什么都不做。
- 破坏性操作提供 `--dry-run` 预览：`apply-rules` / `apply-decisions` 只计算并报告「会动哪些、哪些被保护拦下」，不改动任何文件与清单；`scan --dry-run` 与 `--apply` 互斥，它仍会创建一份不执行隔离的 run 产物并标出 `dry_run`（而非完全不落盘）。
  Web 两条执行接口同样接收 `dry_run`，直接复用 CLI 的执行实现。规则执行条数必须来自后端计划，不能拿规则命中数代替；候选预览使用当前浏览器内存里的决策，不为预览保存或改写 `decisions.json`。
- 每次加载 run 都先清空旧决策再注入已保存决策；切换 run 时同时清空人工保留、候选勾选与隔离区勾选，不能把上一轮的选择带入另一轮。
- 建议档位顺序、标签与说明由后端 `advice` 元数据统一提供；受保护清单优先显示保护原因，内部规则 id 仅作辅助信息。
- `explain <相对路径>`：逐条摊开规则匹配、`when` 条件判定与保护判定（含规则来源），回答「为什么动/不动它」。
  结论必须与真实执行一致：命中目录但子树内含受保护路径时，如实报「整条拦下」并点名是哪个文件挡的，
  不得报「会隔离」——解释与执行给出相反结论比没有解释更危险。
- 本地 Web：加载 run；展示**待自动隔离**（可勾选保留并直接执行自动隔离）、候选与 AI 建议、重复组、
  **受保护清单**、**已隔离清单**；勾选决策并触发执行；对任一路径可就地查看「为什么？」
  （与 CLI `explain` 同一份解释）。
  待自动隔离摆在候选之前，因为它是「不误删」的终审入口——看不到规则打算动什么，终审就无从谈起。

### FR-10 桌面壳（第二期，薄壳）

- `dirtidy desktop [root]`：启动本地服务 → 等就绪 → 自动打开浏览器 → 阻塞直到退出。
- 形态约束：**只做薄壳**，不做 Electron/Tauri 打包与签名。托盘图标是**可选增强**——
  未安装 `pystray` 时降级为「按 Ctrl-C 退出」，不把托盘变成硬依赖；需要托盘时装 `pip install dirtidy[desktop]`。
- 首选端口被占用时自动顺延找空闲端口，不让用户自己去排查「端口冲突」。
- 就绪判定走 HTTP 健康端点而非 TCP 连接：TCP 通了不代表路由已挂好，
  此时打开浏览器会看到连接被拒，比多等 0.2 秒更糟。

### FR-11 定时监视（第二期，只扫描）

- `dirtidy watch [root] [--interval 分钟]`：定期扫描并报告**新增**的命中项。
- **硬边界：只扫描，绝不执行隔离。** 监视天然是「自动触发」，而本工具的核心价值是
  「自动只到候选/隔离区为止，执行必须人工」。自动搬文件等于把保护判定加固全部作废。
  代码层面 `watch` 不得传 `apply=True`，需有测试守护这条不变量。
- CLI、Web 与 `run_watch` 的单轮超时默认值共用 `WATCH_DEFAULT_TIMEOUT`（1800 秒）；Web 可显式设置 `0` 表示不限时，负数拒绝。超时只跳过本轮，不更新比对基线。
- 通知失败（系统不支持、无通知服务）静默降级为控制台输出，不能让监视因通知而中断。

### FR-12 Cursor 状态库清理（独立支线）

- `dirtidy cursor-cleanup [--db PATH] [--days N] [--apply]`：清理 Cursor 全局状态库 `state.vscdb` 中明确过期的会话数据。历史库规模与取证数据见 [事故记录](cursor-cleanup-integration/事故-20261022-会话无法还原.md)，不能据此推定当前库的构成或可回收量。
- **它不在主流程内**。不读目标目录、不产出 run、不在 Web 界面出现入口——理由见 `docs/01` §4.2。
  要求写在这里，是为了它享有与主流程**同一套**安全约束，而不是因为它是主流程的一环。
- 安全约束（逐条对应 FR-2 / FR-3 / FR-6 的同名承诺）：
  - **默认干跑**：不加 `--apply` 一个字节都不改库。
  - **执行路径不删共享 blob**：会话还原依赖的 tool-result blob 可能在 value 引用扫描里被判成「孤儿」，其引用实际藏在气泡 key 的 `/t:call_<toolCallId>` 协议里。共享 blob 的年龄与完整归属无法证明，`--delete-blobs` 仅用于兼容只读候选统计，`--blob-confirm` 不再授权删除。
  - **toolCallId 守卫**：只读判定（`plan_blob_cleanup`）仍保留守卫——库里存在 `/t:` 工具结果气泡时，tool-result 形态的孤儿计入 `blob_guarded`。统计结果不是可安全删除名单；「无 64 位引用」证明不了「会话还原不需要它」。
  - **绝不删 `ItemTable`**（用户设置：插件 / 主题 / 快捷键）。
  - **blob 候选统计集中在 `plan_blob_cleanup`**，只读分析不得另写一套候选判定；其名单不构成执行许可，清理入口一律拒绝共享 blob 删除。
  - **引用来源必须扫全部非 blob 前缀**：漏掉 `ofsContent:` 这类前缀就会把活数据判成孤儿。
  - **Cursor 在跑就拒绝执行**（改库会抢 WAL 锁）；**判断不了是否在跑也按「在跑」处理**——
    返回「没在跑」的语义是「可以放心改库」，取不到进程列表却放行等于在 Cursor 正写库时拆它的库。
  - **清理范围只许是 `state.vscdb` 及其伴生文件**：禁止访问 `~/.cursor/projects/*/agent-transcripts/`、
    `~/.cursor/chats/`、Chromium `blob_storage` / IndexedDB（源码层有守卫测试）。
  - **近 N 天会话完整保留**：header、`composerData`、气泡、checkpoint 一个不删。
  - 清理前冷备份、压缩后校验，校验不过即中止替换；**备份目录跟着被清理的库走**，不写死用户 HOME。
  - **边清理边记审计**（JSONL，每阶段追加一行，含 `aborted` 与 `blob_refused`）：删 blob 分批做、
    全程几十分钟，只在跑完时落盘等于「被杀就没有任何记录」，而这是不可恢复的删除（对照 FR-6、NFR-12）。
- 默认库路径按平台推导（macOS `~/Library/…`、Linux `~/.config/Cursor`、Windows `%APPDATA%\Cursor`）。

## 2. 非功能需求

| 编号 | 要求 |
|------|------|
| NFR-1 | 支持 macOS、Linux、Windows（路径与换行差异由标准库处理） |
| NFR-2 | 无模型时 Step1 完整可用 |
| NFR-3 | 默认不静默彻底删除 |
| NFR-4 | 超大目录可用 quick 模式降低 hash 成本 |
| NFR-5 | 配置与密钥不入库；示例用 `*.example.yaml` |
| NFR-6 | 扫描常驻内存与文件数线性且系数固定；不构造与 inventory 等长的第二份结构 |
| NFR-7 | 扫描可中断续跑：已算过的内容 hash 不重复计算（SQLite 缓存） |
| NFR-8 | 进度回调按 1% 节流，不因反馈本身拖慢扫描 |
| NFR-9 | 归档解析、重复分组、模型外发均有硬上限，单个异常输入不能拖垮整次运行 |
| NFR-10 | 产物写盘流式化，峰值内存不随产物条数增长 |
| NFR-11 | 产物写盘**原子**：任何时刻读到的都是完整的旧文件或完整的新文件，不存在半个 JSON |
| NFR-12 | 破坏性操作的中断一致性：隔离中途被打断时，**已经搬走**的条目一定在清单里有记录 |
| NFR-13 | 单个坏输入（坏归档、权限不足、磁盘满）不得中止整次运行，记入 `errors.json` 后继续 |

稳定性设计与仍未覆盖的边界见 `docs/08-稳定性与性能设计.md`。

规模目标与实测数据见 `docs/07-规模与性能.md`（500 万条 / T 级数据，内存上限 2 GB）。

## 3. 验收标准（MVP）

1. 夹具目录上：`scan` + `apply-rules` 能隔离 `node_modules`/`__pycache__`/空目录等，并生成审计。
2. 构造「压缩包内文件 hash = 磁盘文件」时，压缩包进入候选而非仅靠文件名。
3. 重复组出现在候选中，未人工决策前不自动隔离组内全部文件。
4. 配置 mock/本地 provider 时 `analyze` 写出 `ai_suggestions.json`。
5. Web 能加载 run 并保存 decisions；`apply-decisions` 生效。
6. `quarantine-restore` 能还原已隔离条目。
7. 审阅页能看到待自动隔离项与受保护清单；勾选保留后执行自动隔离，保留项留在原地且记入 `protection.json`。
8. `node_modules/.env` 这类「受保护文件躺在将被隔离的目录里」的情形，目录被整体拦下，密钥文件原地不动，
   且 `protection.json` 留有 `blocked_at=protected_descendant` 的记录。
9. `scan --apply` 这条执行路径同样不得带走受保护后代：目录被整体拦下、密钥文件原地不动，
   `meta` 单列 `protected_blocked_by_descendant` 计数（`protected_blocked` 保持「命中保护清单」原语义，两者不混算）。
