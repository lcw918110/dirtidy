# dirtidy — 规模与性能（非功能需求）

本文区分三类信息：§1 是规模目标，§3 是样本测量后的预算推算，§5 是本机合成树实测，并非 500 万条完整扫描的验收报告。先看目标与 §6 边界，再按需读预算和历史测法修正；稳定性设计见 [08](08-稳定性与性能设计.md)。

## 1. 目标规模

这里的「规模」指**单机、单用户、单次扫描**能处理的目录树大小。dirtidy 是本地后台程序而非服务端：
没有并发用户，也没有「多人在线」这回事。所以下面这些数字衡量的是「**一次运行要占多少内存**」——
500 万指的是**一次扫描遇到的条目数**，与用户数无关。

| 维度 | 目标 | 说明 |
|------|------|------|
| 文件数 | **500 万条** | 单次扫描的 inventory 总量（含目录条目） |
| 数据量 | **T 级** | 总容量本身不影响内存，只影响 hash 阶段耗时 |
| 单目录宽度 | 10 万项 | 不能因为 `listdir` 一次性展开而爆内存 |
| 内存上限 | **≤ 2 GB**（500 万条） | 见 §3；按条目样本外推，选择性 hash（1/20 比例）的条目常驻约 **1.07 GB**，全量 hash 对照约 1.55 GB、quick 约 1.05 GB；不是整次扫描峰值的实测保证。2 GB 目标的依据见 §3.2 |
| 磁盘额外占用 | ≤ 目标数据的 0.1% | inventory 与哈希缓存 |

明确**不做**的事：不保证在 32 位或可用内存 < 3 GB 的机器上跑 500 万条
（2 GB 是进程自身占用，另需给解释器与系统留余量）。
规则是「先量出来再优化」，不靠感觉。

## 2. 非功能需求条目

| 编号 | 要求 |
|------|------|
| NFR-6 | 扫描常驻内存与文件数**线性且系数固定**，不出现与「全量字典/全量列表」相关的额外倍数 |
| NFR-7 | 扫描可中断、可续跑：已算过的内容 hash 不重复计算 |

## 3. 内存预算模型

单条 `InventoryItem` 实测 **325.1 B**（`dataclass(slots=True)`，含各自的路径字符串、
mtime 与 sha256）。**但默认路径不会给每条都存 sha256**——只对必要的那批算（见 §3.2），
因此按 1/20 的选取比例实测是 **225.3 B/条**。500 万条的常驻账如下：

| 项 | 500 万条 | 说明 |
|----|----------|------|
| `items` 列表本体 | 约 1.05 GB | 225.3 B/条（选择性 hash，默认路径），**唯一必须全量驻留的结构** |
| 选桶临时集合 | 约 0.25 GB | 判断「哪些 size 出现 ≥2 次」用的 `set`，返回后即释放；最坏情形见 §3.2 |
| 规则匹配索引 | 约 0.04 GB | `_PathIndex` 只多一份排序后的路径指针数组（8 B/条） |
| 命中 hash 表 | < 0.01 GB | `select_hashes()` 只为待隔离条目取 hash |
| 哈希缓存 | 约 0 GB 常驻 | SQLite 逐条/批量查，不整份载入 |
| 归档磁盘 hash 集合 | 0 或约 0.03 GB | 仅当存在 zip/tar 时才构建，且只含被算过 hash 的那批；无归档直接跳过 |
| inventory 写盘 | 约 0 GB | `write_json_stream` 边生成边写，峰值一行 |
| **合计** | **约 1.10 GB（稳态）／1.35 GB（含选桶瞬态）** | 上限 2 GB，留足余量 |

作为对照，改造前同一场景的账：`items` 1.08 GB + `by_path` 全量字典 0.4 GB +
`hash_map` 全量字典 0.4 GB + inventory 的 dict 列表与 JSON 文本各约 1.2 GB →
**3.3 GB 常驻 + 约 2 GB 瞬时尖峰**。差别全部来自「不要构造第二份等长的东西」。

### 3.1 为什么数字比旧版高：一次测量方法的修正

旧版这张表按 **204 B/条** 算，得出「约 1.0–1.5 GB，落在上限内」。那个 204 B 是用
`mtime=1.0`、`suffix=".py"` 这类**字面量**做样本测出来的——字面量被解释器共享，
于是每条少算了 mtime（24 B）与后缀（57 B）两份对象。真实扫描时每条都有各自的
mtime 与后缀，204 B 是乐观值。

把测法改成「每条都造新对象」后的实测（`scripts/bench_scale.py`）：

| 结构 | B/条 | 500 万条 |
|------|------|----------|
| 第一期（含 `suffix` 字段） | 377.0 | 1798 MB |
| 第二期（去掉 `suffix`，全量算 hash） | 325.1 | 1550 MB |
| **第三期默认（去掉 `suffix` + 选择性 hash，按 1/20 比例）** | **225.3** | **1074 MB** |
| 对照：无 `slots` 的等价对象 | 365.1 | 1741 MB |

再按「要不要算 hash」拆开看，差距全在 `sha256` 上：

| 形态 | B/条 | 500 万条 |
|------|------|----------|
| 全量算 hash（第二期默认，现已不是默认） | 325.1 | 1550 MB |
| **选择性 hash（第三期默认）** | **225.3** | **1074 MB** |
| quick（完全不算 hash） | 220.0 | **1049 MB** |
| 目录条目（无 sha256） | 181.4 | 865 MB |

> 选择性 hash 的 225.3 B/条 是**按 1/20 选取比例**测的对照点；真实比例取决于目录内容
> （见 §3.2），通常比 1/20 更低，因此实际常驻更接近 quick 那一档。

> 教训：内存预算必须拿**真实形态**的对象去量。用字面量做样本会把共享开销算漏，
> 而这类误差不会在功能测试里暴露，只会等到真实数据上 OOM。

### 3.2 选择性 hash：为什么只算一部分也正确

第三期把「非 quick 就对**所有**文件算 sha256」改成只算：

```text
{size 出现 ≥2 次的文件}  ∪  {size 命中某个归档成员的文件}
```

依据是两条同 size 的必要性，**不是启发式**：

1. 重复组的定义是内容相同 ⇒ 必然同字节数。所以「size 只出现一次」的文件不可能有重复，
   给它算 hash 没有任何去处；
2. 归档残留对照要求磁盘文件与成员内容相同 ⇒ 必然同字节数。所以磁盘侧只需算
   「size 落在成员 size 集合里」的那批。

于是漏算的文件既不可能重复、也不可能与归档成员相同——**结论与全量算完全等价**。
这条推理是整套优化的全部依据；`docs/03` §3.1 记了它的执行顺序（归档解析必须早于 hash），
`tests/test_scale.py::test_selective_hash_does_not_miss_archive_extraction` 守着它。

**代价**：判断「哪些 size 出现 ≥2 次」绕不开一个与文件数同阶的集合。
最坏情形（所有 size 互不相同）实测 **52.4 B/条**，5M 约 250 MB，函数返回后即释放。
它装的是 `items` 里已有的 int 对象引用，不新造整数；净账仍是 1550 MB → 1074 MB（稳态）。

**为什么上限是 2 GB**：1.5 GB 这个数字是在「旧版预算模型按 204 B/条 算」的前提下定的，
修正测法后真实值是 1.55 GB——**那不是新引入的开销，而是原先就没算准**。
dirtidy 是单机单次运行的后台程序，1.55 GB 是一个进程一次运行的内存峰值，不是服务端并发预算；
现代机器 16 GB 内存起步，这个量级完全够用；且 500 万条本身是极端场景，
典型场景（10 万–100 万文件）占用只有 30–300 MB。相应地「保证线」也上移：
原先是「不保证可用内存 < 2 GB 的机器跑 500 万条」，现在是「不保证 < 3 GB」。

**仍然记在案、已登记为待办的优化路径**（见 `docs/06` 待办台账 T-8、T-10）：

1. ~~重复检测改为「先按 size 分桶，只对同 size 的文件算 hash」~~ —— **第三期已落地**，
   且重构面比原先估的小：只要把归档解析拆成独立的 `probe_archives` 一步、跑在 hash 之前即可；
2. `sha256` 由 64 字符 hex 改存 32 字节 raw：约省 40 B/条（约 190 MB）。属「存得更省」，
   不如第 1 条根本；→ **T-8**
3. 或把目标规模下调到约 350 万条（不推荐——那是适用边界，不是服务能力）。→ **T-10**

## 4. 采用的手段

| 手段 | 解决的问题 | 位置 |
|------|------------|------|
| `dataclass(slots=True)` | 每条省 40 B（500 万条约 200 MB） | `models.py` |
| 不存 `suffix`，按需 `suffix_of(path)` 现算 | 每条省 52 B（500 万条约 248 MB）；全项目只有规则匹配一处读它 | `models.py` / `rules/engine.py` |
| **选择性 hash**：`probe_archives` + `hash_items(sizes=…)` | 只对必要文件算 sha256。实测 325.1 → **225.3 B/条**；字节口径只读 5.0%，扫描耗时 0.51s → 0.04s | `hashing/content.py` / `scan/scanner.py` / `pipeline.py` |
| 产物原子写（临时文件 + `os.replace`） | 崩溃不会留下半个 JSON。**稳定性**手段，对内存与耗时中性 | `models.py` |
| `_PathIndex`（排序数组 + `bisect`） | 去掉规则匹配的全量 `{path: item}` 字典 | `rules/engine.py` |
| `select_hashes()` | 去掉全量 `{path: sha256}` 字典 | `models.py` / `pipeline.py` |
| `write_json_stream()` | 去掉等长 dict 列表 + 整段 JSON 文本 | `models.py` / `audit/writer.py` |
| `iter_json_array()` | 去掉 `json.loads` 的约 2.6 倍解析放大 | `models.py` / `ai/providers.py` |
| SQLite 哈希缓存 | 缓存常驻内存归零；改为增量 upsert，不再每轮重写全量 | `scan/hashcache.py` |
| 扫尾改为「只处理隔离条目的祖先」 | 原来最多 8 轮全树 `os.walk`，改为与隔离条目数成正比 | `quarantine/store.py` |
| 进度回调按 1% 节流（上限 500 条一次） | 原来每个文件一次 Python 回调 | `scan/scanner.py` |
| 归档解析预算 | 成员数 / 解压字节上限，超限转「待人工」 | `hashing/content.py` |
| 重复组与模型外发上限 | 单个超大重复组截断；`summary.max_targets` 给外发封顶 | `hashing/content.py` / `ai/providers.py` |

### 4.1 为什么哈希缓存换成 SQLite

旧实现 `.dirtidy/hash_cache.json` 有两条硬伤，在百万文件下都致命：

1. **读**：`json.loads` 把整份文本与解析结果同时留在内存，500 万条缓存常驻上 GB；
2. **写**：每轮扫描把全量缓存重写一遍，缓存 1 GB 就要再写 1 GB。

SQLite 版本查一批是一次 `TEMP 表 JOIN`（只把命中项拿回 Python），写一批是一次
`executemany` upsert，删旧行是一条 `DELETE ... WHERE scan_id <> ?`。
首次运行会自动把旧的 `hash_cache.json` 导入并改名为 `.json.migrated`，不丢历史进度。

## 5. 实测数据

复现命令（合成树建在 `.bench-tmp/`，跑完即删）：

```bash
python scripts/bench_scale.py --files 1200
```

本机（Apple Silicon / macOS，Python 3.12）实测：

```
[1] 条目内存（50000 条样本）
  InventoryItem（slots=True）    325.1 B/条   1M=  310.0 MB   5M=  1550.1 MB
  第二期：仅 1/20 带 sha256     225.3 B/条   1M=  214.8 MB   5M=  1074.2 MB
  对照：含 suffix 的旧结构      377.0 B/条   1M=  359.6 MB   5M=  1797.8 MB
  对照：无 slots 的等价对象     365.1 B/条   1M=  348.2 MB   5M=  1740.8 MB
  选桶（全 unique size 的最坏情形）：0.003s，峰值额外  52.4 B/条 (5M=  250 MB，返回后即释放；dups=0)

[2] 合成目录树：1200 文件
  scan_tree(quick)    3890 条 / 0.24s (16361 条/s)
  scan_tree(full )    3890 条 / 0.51s ( 7690 条/s)
  pipeline(选择性)    3890 条 / 0.04s  算 hash 521/1320 文件（39.5%），0.02/0.49 MB（5.0%；选桶+解析归档 0.000s）

[3] inventory 读写
  写盘  流式 峰值 0.2 MB / 0.10s   朴素 峰值 4.6 MB / 0.09s
  读回  流式 3890 条 / 0.01s / 峰值 0.2 MB   json.loads 3890 条 / 0.02s / 峰值 1.8 MB
```

结论：

- **条目内存**：默认路径 **225.3 B/条**（选择性 hash，按 1/20 选取比例）；全量算 hash 是
  325.1 B/条。旧版的 204 B/条 是用共享字面量做样本得出的乐观值，见 §3.1；
- **选择性 hash 的收益主要在 IO**：算 hash 的**文件数**降到 39.5%，但**字节数**只降到 5.0%
  ——会被重复/归档命中的通常是小文件，真正占 IO 的大文件基本只出现一次。合成树上耗时
  0.51s → 0.04s；
- **写盘峰值降约 23 倍**（0.2 MB vs 4.6 MB），耗时不变——省的是内存不是时间；
- **读回峰值降约 9 倍**（0.2 MB vs 1.8 MB），速度反而略快；
- 扫描吞吐约 **1.6 万条/秒**（本机小树，含进程启动）；真实磁盘上主要瓶颈是 `stat`
  与内容 hash，不是 Python 逻辑。

> 合成树刻意混入了「每 3 个里有 1 个同 size」的文件，否则选择率会是 100%，基准就测不出收益。
> 见 `scripts/bench_scale.py::build_tree` 的说明。

> 基准里 `scan_tree` 的峰值 RSS 增量显示为 0，是因为 `ru_maxrss` 是进程高水位，
> 而第 [1] 步已经先把水位抬上去了。要看扫描的真实占用，请单独跑
> `python -c "from dirtidy.scan.scanner import scan_tree; scan_tree('路径', quick=True)"`
> 并观察系统监视器。

## 6. 已知边界

| 边界 | 现状 | 影响 |
|------|------|------|
| `items` 全量驻留 | 225.3 B/条 × 条数 | 500 万条约 1.07 GB，是当前内存下限；再往下要么继续省单条，要么改成流式管道（`docs/06` 待办 T-6） |
| 选桶临时集合 | 与文件数同阶的 `set`，最坏 52.4 B/条 | 5M 约 250 MB 瞬态，返回后释放；不影响稳态占用 |
| 重复文件分组 | 需要 `sha256 → [path]` 字典 | 只含被算过 hash 的那批（不再全量），且已用 `MAX_DUPLICATE_PATHS` 限制单组 |
| 归档磁盘 hash 集合 | 存在 zip/tar 时构建，只含被算过 hash 的那批 | 无归档时直接跳过 |
| 单目录 10 万项 | `os.walk` 逐层处理，可承受 | 未做分片并行（`docs/06` 待办 T-7） |
| hash 阶段 | 单文件上限 `max_hash_bytes`（默认 64 MiB） | 更大的文件不哈希，因此不参与重复/解压判定 |
| 选择性 hash 的正确性前提 | 「同内容必然同字节数」 | 若将来允许「按内容截断比较」之类的不等长判等，此优化立刻失效，必须先重估 |
