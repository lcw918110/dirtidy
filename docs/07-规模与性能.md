# dirtidy — 规模与性能（非功能需求）

## 1. 目标规模

| 维度 | 目标 | 说明 |
|------|------|------|
| 文件数 | **500 万条** | 含目录条目，inventory 总量 |
| 数据量 | **T 级** | 总容量本身不影响内存，只影响 hash 阶段耗时 |
| 单目录宽度 | 10 万项 | 不能因为 `listdir` 一次性展开而爆内存 |
| 内存上限 | **≤ 1.5 GB**（500 万条） | 见 §3；**当前实测约 1.55 GB，略超**，达标路径见 §3.1 |
| 磁盘额外占用 | ≤ 目标数据的 0.1% | inventory 与哈希缓存 |

明确**不做**的事：不保证在 32 位或 < 2 GB 可用内存的机器上跑 500 万条。
规则是「先量出来再优化」，不靠感觉。

## 2. 非功能需求条目

| 编号 | 要求 |
|------|------|
| NFR-6 | 扫描常驻内存与文件数**线性且系数固定**，不出现与「全量字典/全量列表」相关的额外倍数 |
| NFR-7 | 扫描可中断、可续跑：已算过的内容 hash 不重复计算 |
| NFR-8 | 进度反馈有节流，不因回调本身拖慢扫描 |
| NFR-9 | 归档解析、重复分组、模型外发都有**硬上限**，单个异常输入不能拖垮整次运行 |
| NFR-10 | 写盘采用流式，峰值内存不随产物条数增长 |

## 3. 内存预算模型

单条 `InventoryItem` 实测 **325 B**（`dataclass(slots=True)`，含各自的路径字符串、
mtime 与 sha256）。据此，500 万条的常驻账如下：

| 项 | 500 万条 | 说明 |
|----|----------|------|
| `items` 列表本体 | 约 1.51 GB | 325 B/条，**唯一必须全量驻留的结构** |
| 规则匹配索引 | 约 0.04 GB | `_PathIndex` 只多一份排序后的路径指针数组（8 B/条） |
| 命中 hash 表 | < 0.01 GB | `select_hashes()` 只为待隔离条目取 hash |
| 哈希缓存 | 约 0 GB 常驻 | SQLite 逐条/批量查，不整份载入 |
| 归档磁盘 hash 集合 | 0 或约 0.5 GB | 仅当存在 zip/tar 时才构建；无归档直接跳过 |
| inventory 写盘 | 约 0 GB | `write_json_stream` 边生成边写，峰值一行 |
| **合计** | **约 1.55 – 2.05 GB** | **超出 1.5 GB 目标**，达标路径见 §3.1 |

作为对照，改造前同一场景的账：`items` 1.08 GB + `by_path` 全量字典 0.4 GB +
`hash_map` 全量字典 0.4 GB + inventory 的 dict 列表与 JSON 文本各约 1.2 GB →
**3.3 GB 常驻 + 约 2 GB 瞬时尖峰**。差别全部来自「不要构造第二份等长的东西」。

### 3.1 为什么数字比旧版高：一次测量方法的修正

旧版这张表按 **204 B/条** 算，得出「约 1.0–1.5 GB，落在上限内」。那个 204 B 是用
`mtime=1.0`、`suffix=".py"` 这类**字面量**做样本测出来的——字面量被解释器共享，
于是每条少算了 mtime（24 B）与后缀（57 B）两份对象。真实扫描时每条都有各自的
mtime 与后缀，204 B 是乐观值。

把测法改成「每条都造新对象」后的实测（`scripts/bench_scale.py`）：

| 结构 | B/条 | 500 万条 |
|------|------|----------|
| 第一期（含 `suffix` 字段） | 377.0 | 1798 MB |
| 现在（去掉 `suffix`，按需现算） | 325.1 | 1550 MB |
| 对照：无 `slots` 的等价对象 | 365.1 | 1741 MB |

第二期已把 `suffix` 字段去掉（全项目只有规则匹配一处读它），省 **52 B/条 ≈ 248 MB**，
但 500 万条仍**略超** 1.5 GB。要真正守住上限，按收益排序还有三条路：

1. `sha256` 由 64 字符 hex 改存 32 字节 raw：约省 40 B/条（约 190 MB）；
2. **重复检测改为「先按 size 分桶，只对同 size 的文件算 hash」**——这会大幅减少需要
   计算与常驻 hash 的文件数，比「把 hash 存得更省」更根本；
3. 或把目标规模从 500 万下调到约 350 万条。

> 教训：内存预算必须拿**真实形态**的对象去量。用字面量做样本会把共享开销算漏，
> 而这类误差不会在功能测试里暴露，只会等到真实数据上 OOM。

## 4. 采用的手段

| 手段 | 解决的问题 | 位置 |
|------|------------|------|
| `dataclass(slots=True)` | 每条省 40 B（500 万条约 200 MB） | `models.py` |
| 不存 `suffix`，按需 `suffix_of(path)` 现算 | 每条省 52 B（500 万条约 248 MB）；全项目只有规则匹配一处读它 | `models.py` / `rules/engine.py` |
| `_PathIndex`（排序数组 + `bisect`） | 去掉规则匹配的全量 `{path: item}` 字典 | `rules/engine.py` |
| `select_hashes()` | 去掉全量 `{path: sha256}` 字典 | `models.py` / `pipeline.py` |
| `write_json_stream()` | 去掉等长 dict 列表 + 整段 JSON 文本 | `models.py` / `audit/writer.py` |
| `iter_json_array()` | 去掉 `json.loads` 的约 2.6 倍解析放大 | `models.py` / `ai/providers.py` |
| SQLite 哈希缓存 | 缓存常驻内存归零；改为增量 upsert，不再每轮重写全量 | `scan/hashcache.py` |
| 扫尾改为「只处理隔离条目的祖先」 | 原来最多 8 轮全树 `os.walk`，改为与隔离条目数成正比 | `quarantine/store.py` |
| 进度回调按 1% 节流（上限 500 条一次） | 原来每个文件一次 Python 回调 | `scan/scanner.py` |
| 归档解析预算 | 成员数 / 解压字节上限，超限转「待人工」 | `hashing/content.py` |
| 重复组与模型外发上限 | 单个超大重复组截断；`summary.max_targets` 给外发封顶 | `hashing/content.py` / `ai/providers.py` |

### 4.1 为什么哈希缓存换成 SQLite

旧实现 `.dirtidy/hash_cache.json` 有两条硬伤，在百万文件下都致命：

1. **读**：`json.loads` 把整份文本与解析结果同时留在内存，500 万条缓存常驻上 GB；
2. **写**：每轮扫描把全量缓存重写一遍，缓存 1 GB 就要再写 1 GB。

SQLite 版本查一批是一次 `TEMP 表 JOIN`（只把命中项拿回 Python），写一批是一次
`executemany` upsert，删旧行是一条 `DELETE ... WHERE scan_id <> ?`。
首次运行会自动把旧的 `hash_cache.json` 导入并改名为 `.json.migrated`，不丢历史进度。

## 5. 实测数据

复现命令（合成树建在 `.bench-tmp/`，跑完即删）：

```bash
python scripts/bench_scale.py --files 1200
```

本机（Apple Silicon / macOS，Python 3.12）实测：

```
[1] 条目内存（50000 条样本，每条都造新对象）
  InventoryItem（slots=True）    325.1 B/条   1M=  310.0 MB   5M=  1550.1 MB
  对照：含 suffix 的旧结构      377.0 B/条   1M=  359.6 MB   5M=  1797.8 MB
  对照：无 slots 的等价对象     365.1 B/条   1M=  348.2 MB   5M=  1740.8 MB

[2] 合成目录树：1200 文件
  scan_tree(quick)   3890 条 / 0.26s (15135 条/s)
  scan_tree(full )   3890 条 / 0.28s (13864 条/s)

[3] inventory 读写
  写盘  流式 峰值 0.2 MB / 0.11s   朴素 峰值 5.4 MB / 0.10s
  读回  流式 3890 条 / 0.01s / 峰值 0.2 MB   json.loads 3890 条 / 0.02s / 峰值 2.1 MB
```

结论：

- **条目内存**：真实形态 **325 B/条**（含各自的 mtime 与 sha256）。旧版的 204 B/条 是
  用共享字面量做样本得出的乐观值，修正测法后见 §3.1；
- **写盘峰值降约 27 倍**（0.2 MB vs 5.4 MB），耗时不变——省的是内存不是时间；
- **读回峰值降约 10 倍**（0.2 MB vs 2.1 MB），速度反而略快；
- 扫描吞吐约 **1.4 万条/秒**（本机小树，含进程启动）；按此线性外推，500 万条约 6 分钟
  （真实磁盘上主要瓶颈是 `stat` 与内容 hash，不是 Python 逻辑）。

> 基准里 `scan_tree` 的峰值 RSS 增量显示为 0，是因为 `ru_maxrss` 是进程高水位，
> 而第 [1] 步已经先把水位抬上去了。要看扫描的真实占用，请单独跑
> `python -c "from dirtidy.scan.scanner import scan_tree; scan_tree('路径', quick=True)"`
> 并观察系统监视器。

## 6. 已知边界

| 边界 | 现状 | 影响 |
|------|------|------|
| `items` 全量驻留 | 325 B/条 × 条数 | 500 万条约 1.55 GB，是当前内存下限；再往下要么继续省单条（sha256 存 raw、按 size 预筛 hash），要么改成流式管道（见 §3.1） |
| 重复文件分组 | 需要 `sha256 → [path]` 字典 | 全盘同内容时字典会显著增长，已用 `MAX_DUPLICATE_PATHS` 限制单组 |
| 归档磁盘 hash 集合 | 存在 zip/tar 时约 0.5 GB | 无归档时已跳过 |
| 单目录 10 万项 | `os.walk` 逐层处理，可承受 | 未做分片并行 |
| hash 阶段 | 单文件上限 `max_hash_bytes`（默认 64 MiB） | 更大的文件不哈希，因此不参与重复/解压判定 |
