| 扫描内存（中间路线） | 去掉 `InventoryItem.suffix` 字段，改为 `suffix_of(path)` 现算 | 只动 `models` / `scanner` / 规则匹配点，不碰规则与隔离链路 |

### 顺带查出的两处「文档说的和做的不一样」

1. **`docs/07` 的内存预算模型偏乐观**。旧版按 204 B/条 算出「5M 条约 1.0–1.5 GB，落在上限内」，
   但那个数字是用 `mtime=1.0`、`suffix=".py"` 这类**字面量**做样本测的——字面量被解释器共享，
   每条少算了 mtime 与 suffix 两份对象。改成「每条都造新对象」重测后：
   第一期结构 377 B/条（5M ≈ 1.80 GB），去掉 `suffix` 后 325 B/条（5M ≈ 1.55 GB）。
   据此把内存上限从 1.5 GB 调整为 **2 GB**（依据见 `docs/07` §3.2）。
2. **`bench_scale.py` 的 docstring 与实现不符**：声称「合成树建在系统临时目录下」，
   实际建在 `Path.cwd()/.bench-tmp`。已订正说明，并写清「在会拦截工作目录批量删除的环境里，
   请先换到一个可自由删除的目录再跑」。

> 这两处都不是新引入的功能 bug，而是**度量本身不准**——比功能 bug 更隐蔽：
> 它不会让任何用例变红，只会在真实数据上以 OOM 的形式出现。

## 第三期（2026-10-10）：按「后台程序」重做定位与稳定性

明确了「dirtidy 是一个**偏后台的程序**，稳定性与性能要多做设计和考虑」，据此做三件事。

### 1. 定位收口

`docs/01` §1 写明「**单机、单用户的后台程序**」，并按后台程序的标准要求稳定性。
相应地，`docs/01` §4「不做」里**彻底去掉**了「企业账号体系、多租户」——
不再作为议题出现，而不是标成「非目标」后一直挂着。

### 2. 稳定性落地两项（新增 `docs/08-稳定性与性能设计.md`）

| 项 | 落地 | 为什么 |
|----|------|--------|
| 产物原子写 | `write_json` / `write_json_stream` / `audit.md` 改为「同目录临时文件 + `os.replace`」 | 后台进程可能被 SIGKILL / OOM 杀。直接写会留下**截断**的 JSON，读者看到的是「数据损坏」而不是「这次没跑完」——排查方向会被带偏到文件系统上 |
| 隔离清单崩溃一致 | `quarantine_hits` 的清单写入放进 `finally` | 原先整批搬完才写清单，中途被打断会留下「文件已离开原位、清单里却查不到」——用户不知道文件去哪了，也无从还原。这是本工具最不能出的错 |

同时把盘出来的五条未覆盖边界（硬杀、并发实例、超时、磁盘预检、产物清理）
登记为待办 T-1 ～ T-5，都带触发条件与验收标准。

### 3. 性能落地：选择性 hash

原先非 quick 扫描对**所有**文件算 sha256。现在只算
「size 出现 ≥2 次」∪「size 命中某个归档成员」的文件——依据是「同内容必然同字节数」，
所以没被算到的文件既不可能重复、也不可能与归档成员相同，**结论与全量算等价**（不是近似）。

实测（合成树 1200 文件 → 3890 条）：

```
scan_tree(full )    3890 条 / 0.51s
pipeline(选择性)    3890 条 / 0.04s   算 hash 521/1320 文件（39.5%），0.02/0.49 MB（5.0%）
```

单条常驻 **325.1 B → 225.3 B**（5M：1550 MB → 1074 MB），且省下的主要是 IO 时间。

`docs/07` §3.2 当时判断这条「不能顺手改，要先把归档解析提到 hash 阶段之前，属流程重构」——
本轮正是这么做的，并发现重构面比原先估的小：把归档解析单独拆成 `probe_archives` 一步、
跑在 `hash_items` 之前即可，不需要动规则匹配与隔离链路。

### 4. 首次推 GitHub：CI 暴露两个「本地看不见」的问题

代码首次推到 GitHub 后，6 个 job 里 Windows 两个版本红，其余 4 个绿。
两条都不是产品缺陷，而是**只在特定平台才成立**的假设：

| 症状 | 根因 | 修法 |
|------|------|------|
| `test_archive_hash_candidate` 报找不到归档残留 | 仓库没有 `.gitattributes`，Windows runner 默认 `core.autocrlf=true`，checkout 时把 `payload.txt` 从 LF 转成 CRLF。size 16 → 17，于是它连「待算 hash 的 size 集合」都进不去，根本不会被 hash；内容也变了，即便算了也对不上 zip 成员 | 新增 `.gitattributes` 对 `tests/fixtures/**` 关掉转换；并加 `test_gitattributes_pins_fixture_bytes` **直接问 git** 该 attribute 是否生效（守语义，不是守文件存在） |
| `test_load_model_config_finds_user_config_dir` 失败 | 测试用 `monkeypatch.setenv("HOME", ...)` 伪造家目录，但 `Path.home()` 在 POSIX 读 `HOME`、在 Windows 读 `USERPROFILE`——设 `HOME` 在 Windows 上是空操作，代码去查了真实用户目录 | 改为 `monkeypatch.setattr("dirtidy.ai.providers.Path.home", ...)`，平台无关 |

顺带发现 `test_missing_config_error_mentions_example_and_env` 在 Windows 上**碰巧通过**：
真实用户目录同样没有配置，也会抛 `FileNotFoundError`，断言就满足了——它其实什么都没验证。
同一批修掉。

**教训**：CI 的价值不是「本地绿了再确认一次」，而是暴露本地平台**结构上看不见**的差异。
上面两条在 macOS 上跑一万次也不会红。用例数 168 → 169。

## 待办台账

技术类开放项此前散在「有意不做」与「记在案但本轮不做」两处，容易被当成「已经决定过的事」
而永远不动。现在统一收进来，每条都写清**触发条件**与**验收标准**——
不写这两样的待办会一直躺在清单里，等到没人记得它为什么在那儿。

优先级：**P0** 影响数据安全；**P1** 影响可用性；**P2** 收益明确但可等待。

| # | 项 | 优先级 | 触发条件 | 验收标准 |
|---|----|--------|----------|----------|
| T-1 | 隔离 append-only 日志 | **P0** | 需要「被 SIGKILL / OOM 硬杀后仍能还原」这一保证时 | `kill -9` 打断隔离后重启，`quarantine-restore --all` 能还原全部已搬条目；有对应用例 |
| T-2 | root 级单实例锁 | P1 | 出现两个进程同时扫同一 root 的真实场景 | 第二个进程给出可操作报错并退出；状态目录不再互相踩 |
| T-3 | 单次运行超时 | P1 | `watch` 因某个慢盘长时间不返回 | 超时后落盘已有进度并报可操作错误；`watch` 能继续下一轮 |
| T-4 | 写盘前磁盘空间预检 | P2 | 出现因 `ENOSPC` 写到一半失败 | 预检不通过时报出所需空间与可用空间；不产生半个产物 |
| T-5 | 产物目录保留策略 | P2 | `.dirtidy/runs/` 堆积影响使用 | 可配置保留最近 N 次；清理有显式确认 |
| T-6 | 扫描全流程流式化 | P1 | 目标规模上调到 >1000 万条，或内存上限压回 1 GB | `items` 不再全量驻留；峰值内存与文件数解耦；全量用例保持绿 |
| T-7 | 单目录分片并行 | P2 | 出现单目录 >50 万项的真实场景 | 单目录 100 万项下扫描时间与目录数线性、内存不翻倍 |
| T-8 | `sha256` 存 32 字节 raw | P2 | 需要再省约 190 MB@5M | inventory 仍能正常读回（hex 只在边界转换）；用例覆盖 |
| T-9 | 桌面原生壳（Electron/Tauri） | P2 | 薄壳的启动门槛仍被抱怨，且愿意承担打包签名与自动更新的长期成本 | 三平台可安装包 + 自动更新通道；**不新增任何执行入口**，行为与薄壳逐字一致 |
| T-10 | 下调目标规模 | — | 目标机器内存普遍 < 3 GB | 已评估，**不建议**：那是适用边界，不是服务能力 |

> - **T-1 ～ T-5** 是写 `docs/08-稳定性与性能设计.md` 时盘出来的稳定性缺口；
> - **T-6 ～ T-8** 来自 `docs/07` §3.2 的优化路径；
> - **T-9** 是形态类远期项——**当前形态约束不变**，仍是薄壳，列出来是为了有个正式入口；
> - **T-10** 是「评估过但不建议做」，列出来是为了避免重复讨论同一件事。

**已落地**：按 size 分桶算 hash（原 `docs/07` §3.2 的第 1 条优化路径，也是收益最大的一条），
第二期完成——见 `docs/07` §3.2 与 `docs/03` §3.1。

### 保护清单不可绕过（2026-10-10）

截图审查审阅页时发现两处「不误删」的破口：

| 项 | 状态 | 说明 |
|----|------|------|
| `apply-decisions` 不检查保护清单 | 已修 | `apply-rules` 有保护复核而 `apply-decisions` 没有——后者就成了绕过保护的缝：网页上把 `id_rsa` 标成 quarantine 就能把它搬进隔离区。两条路径的保护语义不一致，本身就是 bug。现共用同一套判定（`_protect_matchers` 读同一份 rules/protect 来源），被拦下的记入 skipped 并写入 `protection.json`（`blocked_at=apply_decisions`）。`archive` **有意不拦**：它是显式指定目标的归类，文件仍在根内可找回，与「清理」语义不冲突 |
| 0 字节文件被判成重复组 | 已修 | 空文件 sha256 天然相同，全被归成一个「内容相同」的组，把 `.env` / `id_rsa` 这类空占位文件混进去，诱导用户点「其余标记隔离」。现 `find_duplicate_groups` 跳过 `size == 0`；空文件自有 `empty_file` 规则处理（进候选） |

真机验证：走 Web 决策路径隔离 `.env` → `blocked_by_protect=1`，原因写明保护规则，文件留在原地；
重复组只剩 `dup_a.txt`/`dup_b.txt` 两个真重复文件。

### 保护被「搬走父目录」绕过（2026-10-10，第三轮）

做受控仿真目录的真实场景验证时发现的**零配置即可触发**的破口。上一轮把「决策路径不查保护清单」
堵上了，但保护判定本身只看命中路径**的**自己——于是命中一个目录就等于把它内部所有受保护文件
一起搬走：

| 项 | 状态 | 说明 |
|----|------|------|
| 命中目录带走受保护后代 | 已修 | `node_modules` 命中 `dep_node_modules`，而 `node_modules/.env`、`node_modules/id_rsa` 本该由内置清单兜底，却会被连锅端进隔离区，且 `blocked_by_protect` 报 **0**，毫无痕迹。现 `find_protected_descendants` 在**实盘**上遍历命中目录的子树，一旦发现受保护路径就整条拦下，记 `protection.json`（`blocked_at=protected_descendant`，原因写明是哪条规则、保护了什么）。两条执行路径（规则 / 人工决策）共用 `plan_quarantine`，语义一致 |
| 子树不可读时的取舍 | 已定 | 读不动的子树无法证明「里面没有受保护内容」。保护优先于清理，因此按拦下处理并记 `__unreadable__`，宁可不动也不赌它安全 |
| 目录与其内文件重复命中 | 已修 | `src/__pycache__` 与 `src/__pycache__/main.cpython-311.pyc` 同时命中，被当两个独立条目搬。后果是清单多出一条**永远还原不回去**的记录（还原时目标已被父目录的还原创建出来，`restore_entries` 恒跳过），隔离区留下死空目录，dry-run 条数也与真实产物对不上。现 `drop_covered_descendants` 只保留父目录一条 |

为什么在实盘遍历而不是查 `inventory.json` 快照：快照会过期（扫描之后新增的文件不在里面），
且 `.git` / `.dirtidy` 这类被扫描器跳过的目录本就不在快照里——恰恰是保护清单最关心的那些。
代价只与「将要被搬走的目录」大小成正比，且发现第一条受保护路径即早退，不随全树规模增长。

`plan_quarantine` 被设计成**预览与实跑的唯一来源**：`--dry-run` 报出的「会搬哪些、拦下哪些」
与真实执行逐条一致。这一轮的两个 bug 都属于「两处判定各写一份」这一类——同源是唯一的根治办法。

真机验证（零配置，无 `--protect`）：`node_modules/{pkg/index.js, .env, id_rsa}` →
dry-run `would_quarantine=0` / `blocked_by_protect=1`，实跑 `quarantined=0`，三个文件全部原地未动；
嵌套场景 `auto_hits=2` → 清单只剩 1 条，`quarantine-restore --all` 后清单清空为 `[]`、树完整还原。

### 解释与执行结论不一致（2026-10-10，第四轮）

上一轮堵住漏洞后，接着追问「还有没有别的地方各写一份判定」，果然在**解释侧**找到第三个实例：

| 项 | 状态 | 说明 |
|----|------|------|
| `explain` 报「会隔离」而 apply 实际整条拦下 | 已修 | 实测 `explain node_modules` → 「结论: 自动隔离——apply-rules / --apply 时会移入隔离区」，而 `apply-rules --dry-run` → `would_quarantine: 0` / `blocked_by_protect: 1`。用户照着一份错的说明做决策，比没有说明更糟。现 `explain` 对目录复用执行侧的 `find_protected_descendants`，报「整条拦下」并点名是哪个文件挡的 |
| 拦下理由查不到责任人 | 已修 | 原先 `protect_reason` 只说「子树内含受保护路径」，用户不知道是哪个文件。现 `find_protected_descendants` 返回 `(受保护路径, 规则 ID, 原因)`，`protection.json` 多一个 `blocking_path` 字段，解释里直出「子树内的受保护路径: node_modules/.npmrc」 |

**为什么不拿 explain 已枚举的 items 去查**：`explain` 枚举后代时按 `SKIP_DIR_NAMES` 跳过了
`.git`，而 `.git` 恰恰是保护清单最关心的；且枚举有 20000 条上限，截断就等于给出错误答案。
因此这里走的是与执行同一份、不剪枝也不截断的遍历。

至此「同一件事两处判定」的三个实例（`apply-decisions` 漏查保护、`plan_quarantine` 与实跑各算一遍、
`explain` 自算结论）都已收敛到同一份实现上。但还有第四个，藏在第三条执行路径上——见下节。

### `scan --apply` 绕过保护（2026-10-10，第五轮）

接着追问「所有会搬文件的路径都查过保护了吗」，在 `scan --apply` 上找到第四个实例：

| 项 | 状态 | 说明 |
|----|------|------|
| `scan --apply` 不查保护 | 已修 | 实测 `scan --apply` 把 `node_modules` 连同其中的 `.npmrc`、`id_rsa` 一并端走，`protected_blocked: 0` 且无任何告警。`apply-rules` / `apply-decisions` 上一轮已修，唯独这条路径漏了 |
| `meta` 两类计数混算 | 已修 | 新增 `protected_blocked_by_descendant` 单列「因子树含受保护路径被整条拦下」；`protected_blocked` 保持「命中保护清单」原语义，避免 `scan` 与 `scan --apply` 对同一棵树报出不同数字 |

**为什么不是「再补一处调用」**：`is_protected` 原先在 `quarantine_hits` 里是可选参数，
于是每个调用方都能「忘了传」，而且忘了不会报错——保护静默失效，正是最危险的失效方式。
本轮已经补了第三处调用，再补第四处意味着还会有第五处。改成**必填 keyword-only** 之后，
漏传直接 `TypeError`，把「可能忘」变成「跑不起来」。

改完立刻见效：`tests/test_scale.py` 里两处直接调用 `quarantine_hits` 搭场景的旧代码
在收集期就报 `TypeError`，被一并揪出来。必填参数不只保护生产代码，连测试也扫了一遍。

唯一保留的「空判定器」是 `sweep_empty_dirs` 处理当场确认为空的目录时的 `nothing_protected`——
漏洞在数学上不成立，且写成一个有名字的函数让这个例外在调用处一眼可见，而不是看起来像漏传。

### `.workbuddy-ai/` 为什么不入库（2026-10-10）

`.workbuddy-ai/` 是 AI 工具的项目记忆目录，内容为工作日志（2 个文件、357 行、28 KB）。
已加进 `.gitignore`。判断依据：

| 维度 | 结论 |
|------|------|
| 是否含敏感信息 | **无**。扫描未见真实密钥（命中的都是 `builtin_protect_credentials` 这类技术术语），本机绝对路径 0 处 |
| 是否项目资产 | 不是。工具私有目录，协作者用别的 AI 工具克隆后会困惑「这是项目的一部分吗」 |
| 内容是否唯一 | 不是。设计决策在 `docs/03/04/07`，缺陷与修复在本文档，memory 不是唯一载体 |
| 独特部分性质 | 环境特定（沙箱 pytest 参数、本机 venv 版本），换台机器就不成立 |
| 变动频率 | 高。每次 AI 会话都可能改，会淹没真实代码改动、污染 `git log` |

**所以不是「有敏感信息所以不能入库」，而是「本来就不该入库」。**
跨项目可复用的经验已上迁到用户级记忆与 skill，不依赖这个目录存活。
