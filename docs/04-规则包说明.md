# dirtidy — 规则包说明

选规则包看 §1，判断执行后果与保护边界看 §2，查规则 ID、匹配类型和 `when` 字段看 §3。本文是规则参考；完整操作步骤见 [使用手册](09-功能与使用汇总.md)。

## 1. 内置包

| 包 | 文件 | 用途 |
|----|------|------|
| default | `src/dirtidy/rules/packs/default.yaml` | 通用高置信清理 |
| server_workspace | `src/dirtidy/rules/packs/server_workspace.yaml` | 服务器/交接类工作区（含日志目录、target/vendor 等） |

可复制修改后用 `--rules` 指定。`server_workspace` 通过 `extends: default` 继承全部基础规则。

## 2. 置信分层

| action | 行为 |
|--------|------|
| `protect` | **最高优先级**。命中路径（目录含整棵子树）永不自动隔离，也不进候选，只在 `protection.json` / `audit.md` 里登记 |
| `auto_quarantine` | `apply-rules` / `--apply` 时移入隔离区 |
| `candidate_only` | 只进 `candidates.json`，待人工或决策 |

### 2.0 `purge_safe`：可选的「建议直删」标记

`auto_quarantine` 规则可以加一个可选字段：

```yaml
- id: dep_os_metadata
  action: auto_quarantine
  purge_safe: true          # 重建成本为零，界面会把它标成「建议直删」
  match:
    type: file_name
    names: [".DS_Store", "Thumbs.db", "desktop.ini"]
  reason: "操作系统生成的元数据文件"
```

**它不改变任何默认行为**：默认一律只进隔离区，一条直删都不开。`purge_safe` 只是给界面
一个推荐标记——用户可以在「规则」页把这类规则逐条设为「隔离后立即物理删除」，省下隔离区
的占用。当前标记了 `dep_python_cache`、`dep_os_metadata`、`dep_editor_swap`、`dep_python_bytecode`
四条（缓存目录、系统元数据、编辑器交换文件、字节码）。

直删**不是绕过隔离的另一条路径**，而是隔离路径上多加的一步：

```text
规则命中 → 过 keep 与保护复核 → 搬入隔离区 → 写清单 → 立刻物理删除该条 → 记入 purged_directly.json
```

保护判定与清单写入一个环节都不少，因此「保护」和「可审计」都不会因为开了直删而失效：
子树里躺着受保护路径的目录照样被整条拦下，被人工勾了「保留」的项照样不动。
删除明细单独记在 `purged_directly.json`——那些文件已经不在磁盘上，隔离清单里也不会再有它们，
不另记一笔就完全查不到「谁删的、何时删的」。

开关状态存在状态目录的 `settings.json` 的 `auto_purge_rules` 里，**CLI 与 Web 读同一份**，
不会出现「网页里开了直删、命令行跑却只隔离」。

### 2.0.1 `recover`：删了怎么恢复

会动文件的规则（`auto_quarantine` / `candidate_only`）都应写一句 `recover`：

```yaml
- id: dep_node_modules
  action: auto_quarantine
  match:
    type: dir_name
    names: ["node_modules"]
  reason: "Node / 前端依赖目录，可用包管理器重建"
  recover: "npm install（或 yarn / pnpm install）"
```

界面把它显示成「**删了怎么办：npm install**」——这比「可以清理」有用得多：
用户真正要判断的不是「这条规则安不安全」，而是「我删了之后要付什么代价」。

写法约定：

| 情形 | 怎么写 | 例 |
|------|--------|-----|
| 自动重建 | 「无需恢复，…」 | `无需恢复，下次运行自动重建` |
| 有明确命令 | 直接写命令 | `npm install`、`python -m venv .venv` |
| 可重新获取 | 「需要时重新下载」 | 安装包、临时文件 |
| **删了就没了** | 「无法恢复，…」 | `无法恢复，可能存着唯一副本` |

**「无法恢复」是给用户的刹车，不是免责声明**：压缩包、备份、本地数据库往往存着唯一副本，
界面上必须让他们看到这四个字。`protect` 规则不需要写（它们根本不会被动）。

`tests/test_advice.py::test_every_actionable_rule_explains_how_to_recover` 守着这条：
新增会动的规则却忘了写 `recover`，用例直接红。

### 2.0.2 `label`：规则的中文短名

```yaml
- id: dep_node_modules
  label: "Node 依赖"
  action: auto_quarantine
  match:
    type: dir_name
    names: ["node_modules", "bower_components", "jspm_packages"]
  reason: "Node / 前端依赖目录，可用包管理器重建"
  recover: "npm install（或 yarn / pnpm install）"
```

`label` 回答的是「**这是哪一类东西**」，`reason` 回答的是「**为什么判它**」。两者都要有：

| 字段 | 例 | 出现在哪 |
|------|-----|---------|
| `label` | `Node 依赖` | 审阅页「这是什么」下的小字、扫描页分组、规则页第一列 |
| `reason` | `Node / 前端依赖目录，可用包管理器重建` | 同上的主说明行 |
| `recover` | `npm install` | 「删了怎么办」 |

不写 `label` 时界面回落到 `rule_id`（`dep_node_modules`）——排查时得看得到编号，
但它不该是用户看到的第一信息。内置包 24 条规则全部写了，由
`tests/test_convenience.py::test_every_rule_has_chinese_label` 守着：
新增规则漏写、或把 `label` 直接抄成 `id`，用例都会红。

### 2.1 保护（protect）语义

- 判定**不受规则书写顺序影响**：把 `auto_quarantine` 写在 `protect` 前面也不会误删，
  实现上对每条规则命中的路径单独复核保护清单，而不是先到先得。
- `dir_name` 命中的是**整棵子树**：`.git` 被保护 ⇒ `.git/objects/...` 不可能被自动搬走。
- 命中保护 = 既不隔离、也不进候选。原因：候选区是给人点「隔离」的，把密钥/版本库放进去
  等于给了误操作入口；但审计里逐条列出「哪条规则想动它、被哪条保护规则挡下」，不会静默吞掉。
- 隔离阶段会**再复核一次**：`apply-rules` 在真正搬文件前用当前生效的保护清单重查
  `pending_auto_hits`，防止 pending 列表被改过或规则包换过之后绕过保护。
- 内置清单写在 `src/dirtidy/rules/protect.py`，**不可被规则包关掉**；规则包只能追加自己的 `protect` 规则。
- 追加方式：`dirtidy scan <root> --protect rel/path`（可重复），等价于给该路径及其子树加一条 protect 规则。
- 判定是**双向**的，缺任何一向保护都能被绕开：
  - **向下**：目录命中保护 ⇒ 其整棵子树受保护（见上）。
  - **向上**：一个命中 `auto_quarantine` 的目录，若子树内含受保护路径 ⇒ **整条命中被拦下**。
    否则「保护」会被「搬走它的父目录」这条捷径绕开——`node_modules` 命中 dep 规则时，
    `node_modules/.env`、`node_modules/id_rsa` 就会被一并端走，且 `blocked_by_protect` 报 0、毫无痕迹。
    拦下后记入 `protection.json`（`blocked_at=protected_descendant`，写明是哪条保护规则、保护了什么）。
  - 子树**读不动**时无法证明「里面没有受保护内容」⇒ 同样按拦下处理（`protect_rule_id=__unreadable__`）。
    保护优先于清理，宁可不动也不赌它安全。
  - 检查在**实盘**上遍历命中目录，不查 `inventory.json` 快照：快照会过期（扫描后新增的文件不在里面），
    且 `.git` / `.dirtidy` 这类被扫描器跳过的目录本就不在快照里——恰恰是保护清单最关心的那些。
    代价只与「将要被搬走的目录」大小成正比，发现第一条受保护路径即早退。

### 2.2 隔离计划（plan_quarantine）

`plan_quarantine(root, hits, is_protected=guard)` 把命中列表拆成「可执行」与「被保护拦下」，是**预览与实跑的唯一来源**——
`--dry-run` 与真实执行调用同一个函数；在文件系统和配置未变化时，两者应给出相同计划。预览不是快照，实跑仍需再次复核。顺序不可颠倒：

1. 先按保护拦下「子树内含受保护路径」的目录命中（保护优先）；
2. 再丢弃被覆盖的后代条目——目录与其内文件同时命中时只保留父目录一条。
   否则被拦下目录里的子文件仍会留在列表里，且清单会多出**永远还原不回去**的记录：
   还原时目标路径已被父目录的还原创建出来，`restore_entries` 遇到「目标已存在」恒跳过。

`is_protected` 是**必填参数**，不给默认值。默认值 `None` 会让函数整段跳过保护检查，
把「含受保护后代的目录」原样放进可执行列表——保护静默失效，且预览与实跑同时失效。
这与 `sweep_empty_dirs` 是同一类缺口（见 `docs/06`「2026-10-21 审视：本轮修掉的」），按同一标准收口：**门由签名把住，不靠调用方自觉**。

`dirtidy explain <路径>` 对目录复用同一个 `find_protected_descendants`，因此解释与执行不会分歧；
拦下时会点名是子树里的哪条路径、被哪条保护规则挡住（「子树里有受保护内容」这种说法查不到责任人）。

## 3.1 匹配类型

| type | 字段 | 说明 |
|------|------|------|
| `dir_name` | `names` | 目录名精确匹配 |
| `file_name` | `names` | 文件名精确匹配，仅文件 |
| `name_glob` | `globs`（可配 `is_dir: true/false`） | basename 通配匹配 |
| `suffix` | `suffixes` | 扩展名匹配，仅文件 |
| `empty_dir` | — | 空目录（以文件系统为准） |
| `empty_file` | — | 0 字节且无读取错误的文件 |
| `path_glob` | `patterns` | 相对路径通配匹配 |

## 3.2 条件块 `when`

| 字段 | 说明 |
|------|------|
| `min_age_days` / `max_age_days` | 按 mtime 判断「多久没动过」；mtime 缺失时保守判为不命中 |
| `min_size_bytes` / `max_size_bytes` | **仅对文件生效**（目录大小不聚合） |
| `under` / `not_under` | 路径前缀白名单 / 黑名单 |
| `min_depth` / `max_depth` | 相对根目录的层级 |
| `require` | 守卫列表，目前支持 `source_free`：目录子树内没有源码/构建定义文件才命中 |

`when` 的意义就是「不误删」：单靠目录名判断太糙，加上「多久没动」「多大」「里面还有没有源码」才敢自动搬。

规则包在加载时即校验：未知 `action` / `match.type` / `when` 字段、缺必填字段、id 重复都会直接报错，
不会等到扫完几百万文件才发现笔误。

## 4. 解压残留算法（非 YAML 硬编码逻辑）

1. 对每个归档文件，流式读取成员内容，计算 `sha256`（跳过目录成员）。
2. 在同一扫描根下，收集已计算内容 hash 的文件集合。
3. 若归档内「可哈希成员」中，命中磁盘文件 hash 的比例 ≥ 阈值（默认 0.8，且命中数 ≥ 1），则将该归档标为候选 `archive_extracted`。
4. 加密或无法读取的归档：标 `archive_review`（rule_id=`archive_unreadable`），不自动隔离。加密 zip 抛出的 `NotImplementedError` 也归为不可读。

**禁止**用「同名解压目录」作为充分条件。

## 5. 重复文件

同 `sha256` 且文件数 ≥ 2 → `duplicate_group` 候选；保留策略仅人工。

界面按组报账：**几份 · 每份多大 · 保留一份可释放多少**（逐份字节数由 `path_sizes` 给出，
只在组内路径都算得出来、且没被 `MAX_DUPLICATE_PATHS` 截断时才报可释放量——
截断的组少算几份，报出来的数会偏小）。选一份保留后可一键「其余标记隔离」，
但**只写决策、不搬文件**，仍需到执行页先预览再点「执行候选决策」。

**0 字节文件不参与**：它们的 hash 天然全都相同，凑成的「重复组」没有任何整理价值，
还会把 `.env` / `id_rsa` 这类空占位文件混进来，诱导用户在「其余标记隔离」上误操作。
空文件自有 `empty_file` 规则处理（进候选）。

## 6. 隔离后的空目录

规则包里 `empty_dir` 为 `auto_quarantine` 时，`apply` 之后会多轮把「子项搬走后才空」的父目录一并隔离（最多 8 轮）。目标根本身与 `.dirtidy` 不处理。

## 7. hash 缓存

非 quick 扫描把文件 `path + size + mtime + sha256` 记在目标下 `.dirtidy/hash_cache.sqlite`
（SQLite，见 `scan/hashcache.py`）。未改动的文件下次不再读内容；扫描中断后下次会从未命中缓存的文件继续算。

用 SQLite 而不是 JSON 的原因：JSON 缓存要整份载入、整份重写，百万文件下常驻内存上 GB 且每轮重写全量。
首次运行会自动把旧的 `hash_cache.json` 导入并改名为 `.json.migrated`。
