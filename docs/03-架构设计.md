# dirtidy — 架构设计

## 1. 总览

统一核心库 `dirtidy`；CLI 与本地 Web 均为薄界面，读写同一套 run 产物。

```text
CLI / Web
    │
    ▼
dirtidy 包（scan → rules → hashing → quarantine → audit → ai → decision → web）
    │
    ▼
<root>/.dirtidy/runs/<run_id>/  +  quarantine 目录
```

两个入口模块不参与上面的数据流：`desktop` 只是「起服务 + 开浏览器」的薄壳，
`watch` 反复调用 `scan` + 规则匹配做只读比对。两者都不改变核心链路。

## 2. 模块

| 模块 | 职责 |
|------|------|
| `scan` | 遍历、元数据、**按需**文件 hash（`hash_items(sizes=…)` 只算必要的那批） |
| `rules` | 加载 YAML、匹配、分流 auto/candidate |
| `hashing` | 压缩包成员解析（`probe_archives`，含解压后字节数）、文件 hash 对照、重复组、解压残留判定 |
| `quarantine` | 隔离、还原、彻底清除；`plan_quarantine` 是预览与实跑的唯一来源（先按保护拦下含受保护后代的目录命中，再丢弃被父目录覆盖的后代条目）。保护判定器 `is_protected` 是 `quarantine_hits` 的**必填参数**——`apply-rules` / `apply-decisions` / `scan --apply` 三条路径共用同一份实现，漏传即 `TypeError` |
| `audit` | 写 JSON / Markdown |
| `ai` | Provider 适配、摘要构建、批分析 |
| `decision` | 读写 decisions、apply |
| `settings` | 状态目录里的本地设置：`settings.json`（直删规则清单、是否启用模型分析）与 `models.yaml`（模型接入配置）。**CLI 与 Web 读同一份**，避免两边口径漂移 |
| `deadline` | 协作式单次运行超时：在扫描与 hash 循环里埋检查点，到点抛 `RunTimeout` 并**带出已扫到的部分结果**。刻意不用 `signal.alarm` / 异步异常——那可能落在写文件中间（见 `docs/08` §1.5） |
| `advice` | 把规则动作翻译成用户能直接做判断的话：`advice`（建议清理 / 可以清理 / 需要你判断 / 受保护）与 `effect`（可还原 / 不可还原）。**判定只此一处**——Web 的扫描摘要与审阅列表都从这里取措辞，前端不许再按 `rule_id` 自己算一遍 |
| `web` | FastAPI 应用（含 `GET /api/health` 探活端点） |
| `desktop` | 薄壳启动器：起本地服务 → HTTP 探活 → 开浏览器 → 退出时终止子进程；端口被占用自动顺延，托盘为可选增强 |
| `watch` | 定时监视：定期扫描并与上轮比对，报告新增/消失的命中项；**只扫描，源码里没有任何执行入口**（有静态守护用例） |

## 3. Run 产物

目录：`<root>/.dirtidy/runs/<run_id>/`。

| 文件 | 内容 |
|------|------|
| `meta.json` | run_id、root、时间、选项、命中/保护计数（`protected_blocked` = 命中保护清单；`protected_blocked_by_descendant` = 因子树含受保护路径被整条拦下；两者分开计数，`scan` 与 `scan --apply` 报出的数字才一致）。另含超时三件套：`timed_out` / `timeout`（阶段、秒数、已处理项数）/ `timeout_seconds`——超时的 run **只覆盖一部分目录**，界面与 CLI 都靠它区分「跑完了」与「只跑了一部分」 |
| `inventory.json` | 条目列表（流式写出的 JSON 数组，一行一条）。`sha256` 只对**必要文件**非空——见 §5.3 |
| `candidates.json` | 候选（含重复组、归档残留等） |
| `quarantine_manifest.json` | 已隔离清单 |
| `protection.json` | 被保护清单拦下的路径（想动的规则 + 保护规则） |
| `protect_policy.json` | 本次生效的保护规则摘要 |
| `ai_suggestions.json` | 模型建议 |
| `ai_meta.json` | 外发规模（targets / max_targets / truncated） |
| `decisions.json` | 人工决策 |
| `purged_directly.json` | 命中「直删」规则、搬入隔离区后立即物理删除的条目。**这些文件已不在磁盘上**，隔离清单里也不会再有它们，不另记一笔就完全查不到「谁删的、何时删的」 |
| `audit.md` | 可读摘要 |

`inventory.json` 用 `write_json_stream()` 边生成边写，峰值内存只有一行；
读回用 `iter_json_array()` 增量解析，避免 `json.loads` 的整份放大。详见 `docs/07-规模与性能.md`。

`<root>/.dirtidy/hash_cache.sqlite` 是跨 run 的内容 hash 缓存（SQLite，增量写入）。

状态目录里还有两份**跨 run 的设置**（由 `settings` 模块管理，CLI 与 Web 共用）：

| 文件 | 内容 |
|------|------|
| `settings.json` | `auto_purge_rules`（允许「隔离后立即物理删除」的规则 id，默认空）、`use_model`（是否启用模型分析，默认 false） |
| `models.yaml` | 模型接入配置。格式与项目原有 `models.yaml` 一致，额外允许直接写 `api_key`（明文，供界面填写） |

### 3.1 扫描与 hash 的执行顺序

hash 不是「扫完就全算」，而是**先解析归档、再决定算哪些**：

```text
scan_tree(quick=True)      只扫元数据（路径 / size / mtime）
      │
      ▼
match_rules(...)           规则匹配（不需要 hash）
      │
      ▼
probe_archives(...)        读 zip/tar 成员 → 成员的「解压后字节数」与内容 hash
      │
      ▼
sizes = 出现 ≥2 次的 size  ∪  归档成员 size
      │
      ▼
hash_items(sizes=…)        只对这些文件算 sha256
      │
      ▼
find_duplicate_groups / find_extracted_archives
```

顺序不能倒过来。`find_extracted_archives` 要拿磁盘文件的 hash 与归档成员对照，
而**同内容必然同字节数**——所以「size 命中某个归档成员」就是磁盘侧的必要集，
先解析归档才能算出来。这条推理是整套优化成立的前提，改顺序前先看 `docs/07` §3.2。

`quick=True` 则整段跳过：不解析归档、不算 hash，也就没有重复组与归档残留候选。

## 4. 规则 schema（YAML）

```yaml
pack_id: default
version: 2
rules:
  # 最高优先级：命中即永不自动隔离，也不进候选
  - id: protect_vcs
    action: protect
    match:
      type: dir_name
      names: [".git", ".hg", ".svn"]
    reason: "版本控制元数据，删除即丢失历史"

  - id: log_suffix
    action: auto_quarantine
    match:
      type: suffix
      suffixes: [".log"]
    when:
      min_age_days: 1
    reason: "超过 1 天未更新的日志文件"
```

- `action`：`protect`（最高优先级）/ `auto_quarantine` / `candidate_only`
- `match.type`：`dir_name`、`file_name`、`name_glob`、`suffix`、`empty_dir`、`empty_file`、`path_glob`
- `when`：`min/max_age_days`、`min/max_size_bytes`、`under`/`not_under`、`min/max_depth`、`require` 守卫
- `label`（可选但内置包全写了）：规则的中文短名，如 `Node 依赖`、`旧日志`。
  界面靠它回答「这是什么规则」；没写就回落到 `rule_id`，但 `dep_node_modules`
  这种内部编号摆在列表上只能让人猜（见 `docs/04` §2.0.2）。
- `purge_safe`（可选，默认 `false`）：标记「重建成本为零、确定无用」的规则。
  它**不改变默认行为**（默认一律只进隔离区），只是给界面一个推荐标记：用户可在
  「规则」页把这类规则设为「隔离后立即物理删除」，省下隔离区的占用。
- `recover`（可选但会动的规则都应写）：删了怎么恢复，如 `npm install`、`无需恢复，…`、
  `无法恢复，可能存着唯一副本`。界面显示成「删了怎么办」——说清代价比给个「可以清理」的
  形容词更能让人下决心（见 `docs/04` §2.0.1）。

详见规则包说明。规则包在加载时即校验，笔误直接报错。

## 5. 界面契约（CLI / 本地 Web）

| 命令 | 说明 |
|------|------|
| `dirtidy start [root]` | **★ 一条命令起步**（推荐入口）：没有扫描结果就先扫一次，然后起本地服务并打开浏览器；已有结果则直接开界面（`--rescan` 强制重扫）。给「不想记命令」的人用的最短路径，其余命令都是它的可拆解步骤 |
| `dirtidy scan <root>` | 扫描 + hash/候选（`--quick` 跳过 hash；`--workers` 并行 hash；`--apply` 立即隔离且**同样复核保护清单**，不带走受保护后代；`--protect 相对路径` 追加保护；`--dry-run` 只预览） |
| `dirtidy explain <root> <相对路径>` | 解释该路径会被如何处理：逐条规则匹配、`when` 条件判定、保护判定（`--rules` / `--protect` / `--json`） |
| `dirtidy apply-rules <root> <run_id>` | 对 auto 项执行隔离（`--dry-run` 只列出会搬走哪些、哪些被保护拦下、哪些会被直删；`--keep 相对路径` 本轮保留不隔离）。直删规则清单取自状态目录的 `settings.json`，与 Web 同源 |
| `dirtidy analyze <root> <run_id>` | 调模型写建议 |
| `dirtidy apply-decisions <root> <run_id>` | 执行决策（`--dry-run` 只校验并预览，含同批次归档目标冲突检测） |
| `dirtidy quarantine-restore <root> <run_id> [--all\|--id]` | 还原 |
| `dirtidy purge-quarantine <root> <run_id> --yes` | 彻底清除隔离区 |
| `dirtidy save-decisions <root> <run_id> <file>` | 从 JSON 文件写入 decisions |
| `dirtidy serve [--root DIR] [--run-id ID] [--host H] [--port P] [--reload]` | 本地 Web（`--reload` 仅供开发：改 `src/` 下的 Python 代码自动重启） |
| `dirtidy desktop [root] [--host H] [--port P] [--no-browser] [--no-tray]` | 薄壳启动器：起服务 + 等就绪 + 开浏览器；端口被占用自动顺延，托盘为可选增强（`pip install dirtidy[desktop]`，缺依赖则降级为 Ctrl-C 退出） |
| `dirtidy watch [root] [--rules PACK] [--interval 分钟] [--full] [--rounds N] [--no-notify]` | 定时监视：定期扫描并报告新增命中，**只扫描不执行**；不落盘（不产生 run 产物） |

> 状态目录默认落在 `<root>/.dirtidy/`；设置环境变量 `DIRTIDY_STATE_DIR` 可把它重定位到外部可写目录（用于只读介质）。

### 5.1 `explain` 为什么存在

几百万文件里，用户不可能靠猜知道「这条规则为什么没命中」。`explain` 把判定过程摊开：

```text
$ dirtidy explain /data/ws src/logs
路径: src/logs
类型: 目录   大小: 0 字节

结论: 无规则命中——保持原样
  已枚举后代: 2 条

生效的保护规则 11 条（内置清单 + 规则包 + 额外指定），逐条规则判定如下：

[未命中] builtin_protect_vcs  action=protect  (内置保护)
[命中] log_dir  action=auto_quarantine  (规则包)
    when 条件: 有未通过项
      - min_age_days=3（实际 30.0 天）→ 通过
      - require: source_free（子树内无源码/构建定义文件）→ 不满足
    备注: 路径匹配，但 when 条件不满足 → 本条不生效
[未命中] empty_dir  action=auto_quarantine  (规则包)
```

每行都标了来源：`(内置保护)` 是写在代码里、规则包关不掉的那几条；`(规则包)` 来自 YAML；
`(额外指定)` 来自 `--protect`。**内置清单排在最前**，否则会出现「结论说是 `builtin_xxx`
保护的，但逐条列表里找不到这条规则」——用户查不到责任人。

实现上复用 `rules/engine` 的 `match_items` / `passes_when` / `match_rules`，
单条保护判定复用 `rules/protect` 的 `matcher_hits`，不另写一份解释逻辑——
否则解释结果迟早与真实执行结果漂移，而漂移的解释比没有解释更危险。

**「整条拦下」也必须解释**。命中目录但子树里躺着受保护路径时，apply 会整条拦下
（见 §2 `plan_quarantine`）。解释若还报「会隔离」，用户就会照着一份错的说明做决策：

```
结论: 整条拦下——子树内含受保护路径，apply-rules 时不会隔离
  本来想动它的规则: dep_node_modules（Node / 前端依赖目录，可用包管理器重建）
  子树内的受保护路径: node_modules/.npmrc
  保护规则: builtin_protect_secret_files（密钥 / 凭据文件，误删不可恢复）
  已枚举后代: 2 条
```

（节选：结论段之后还有「逐条保护规则命中明细」与生成时间。）

这一判定复用执行侧的 `find_protected_descendants`，**不拿已枚举的 items 去查**：
`explain` 枚举后代时按 `SKIP_DIR_NAMES` 跳过了 `.git`，而 `.git` 恰恰是保护清单最关心的；
且枚举有 20000 条上限，截断就等于给出错误答案。因此这里走的是与执行同一份、不剪枝也不截断的遍历。

### 5.2 本地 Web 路由

仅绑定 `127.0.0.1`，不设鉴权，勿对公网暴露。页面不加载任何外部资源，由严格 CSP 兜底。
界面按 **概览 / 扫描 / 审阅 / 隔离区 / 规则 / 设置 / 监视** 分页，覆盖 CLI 的全部子命令
（`serve` / `desktop` 本身即入口）。

| 路由 | 对应 CLI | 说明 |
|------|---------|------|
| `GET /` | — | 控制台页面 |
| `GET /api/meta` | — | 当前 root、默认 run、状态目录 |
| `GET /api/health` | — | 探活：桌面壳靠它判断「路由已挂好」，而不是只判断端口通了 |
| `GET /api/runs` | — | run 列表 |
| `GET /api/runs/{id}` | — | 聚合审阅所需产物：候选、AI 建议、决策、**待自动隔离**、**保护清单与生效策略**、已隔离清单、直删留痕、**隔离区占用汇总**、当前直删规则 |
| `POST /api/scan` | `scan` | 新建扫描；body 的 `apply` 为真时顺带执行高置信规则的隔离。**同一时刻只允许一次**，重入返回 409——同时点两次会产生两个 run、两份隔离清单，事后很难对账 |
| `GET /api/scan/progress` | — | 当前扫描进度（`running` / `phase` / `done` / `total`）；界面轮询它显示「已用 N 秒 · 内容 hash 123/456」，避免大目录下看起来像卡死 |
| `PUT /api/runs/{id}/decisions` | `save-decisions` | 保存人工决策 |
| `POST /api/runs/{id}/apply-decisions` | `apply-decisions` | 执行决策 |
| `POST /api/runs/{id}/apply-rules` | `apply-rules` | 执行规则自动隔离；body 的 `keep_paths` 为本轮人工保留项 |
| `POST /api/runs/{id}/analyze` | `analyze` | 调模型写建议；未在设置页启用时返回 400 |
| `POST /api/runs/{id}/restore` | `quarantine-restore` | 还原；body `ids` 或 `all` |
| `POST /api/runs/{id}/purge` | `purge-quarantine` | 彻底删除；body `ids` 或 `all`。按条删除会**同步收敛清单**，界面上的「已隔离」列表因此始终可信 |
| `GET /api/runs/{id}/explain?path=…` | `explain` | 解释该路径为什么被/不被动；返回与 CLI `explain` **逐字一致**的文本 |
| `GET /api/rules` | — | 可用规则包列表 |
| `GET /api/rules/{pack_id}` | — | 规则明细 + 生效保护清单 + `purge_safe` 推荐集 |
| `GET /api/settings` | — | 直删规则、是否启用模型、模型配置状态（**永不回显密钥**）、表单预填值 |
| `PUT /api/settings` | — | 保存直删规则与模型分析开关 |
| `PUT /api/model` | — | 保存模型配置。密钥留空表示**保持原样**，不是清空 |
| `GET /api/watch` | `watch` | 监视状态（运行中/轮次/新增/消失/错误） |
| `POST /api/watch/start` | `watch` | 启动后台监视线程 |
| `POST /api/watch/stop` | — | 停止监视（立即唤醒，不等满一个间隔） |

审阅页把「待自动隔离」摆在候选表之前：这是**不误删的终审入口**——用户必须能先看到
规则打算动什么、哪些已被保护拦下，再决定执行。勾选「保留」的项随 `keep_paths` 提交，
后端本轮不动它们并登记进 `protection.json`（`protect_rule_id=user_kept`）以便审计追溯。

`keep` 的判定是**双向**的，缺任何一向「保留」都会被悄悄绕过：

- **向下**：保留一个目录 ⇒ 它子树内的命中也保留。否则子项被单独搬走 → 目录变空 →
  `sweep_empty_dirs` 再把空壳收走；用户勾的那一项最后还是没了，而且事后在隔离区里
  只能找到子项、找不到那个目录。
- **向上**：保留项落在某个命中目录内部 ⇒ 那个目录本轮也不能动。搬走父目录等于把
  保留项一起搬走。

每条路径旁边有「为什么？」按钮，弹窗直接展示后端 `to_text()` 的文本 —— 与命令行
`dirtidy explain` 是同一份解释，不会出现「网页说的和 CLI 说的不一样」。
页面还支持深链 `/?explain=<相对路径>` 直接打开该弹窗，便于把结论发给别人。

**隔离区页是「中间状态」的操作台**：显示每条占用多少空间与合计占用（实算磁盘占用，
而不是读清单里的 `size`——后者对目录恒为 0，会把用户最关心的数字显示成「0 B」），
支持按条还原 / 彻底删除，以及整体还原 / 清空。彻底删除按条同步收敛清单。

**「直删」不是绕过隔离。** 用户可在规则页把某条 `auto_quarantine` 规则设为直删；
执行时命中项仍走同一条路径——**先过 `keep` 与保护复核、搬入隔离区、写清单**，
然后才物理删除，并在 `purged_directly.json` 留痕。这样「保护」与「可审计」两个环节
一个都不少，直删不会成为绕过保护的缝。默认**一条都不开**。

## 6. 模型输出维度

每条建议含：`asset_type`、`value`、`freshness`、`cluster_id`/`cluster_name`、`sensitivity`、`action`、`suggested_path`、`confidence`、`rationale`。

## 7. 安全摘要

默认字段：相对路径（可脱敏）、ext、size、mtime、kind、`text_sample`（上限可配）、`hash_prefix`。  
完整正文外发默认关闭；有两条显式开启路径——`provider=ollama` 且 `allow_ollama_full_content: true`（本机 Ollama），或 `provider=openai_compatible` 且 `allow_external_content: true`（将正文发往外部端点，需用户显式承担）。

抽样加固（2026-10-09）：

- 文件名命中敏感线索（`credential(s)` / `secret(s)` / `password(s)` / `token(s)` / `api_key` / `id_rsa` / `.env` / `.npmrc` / `.aws` / `.ssh` 等）时**完全不抽样正文**。
- 其余文本若含疑似密钥，用 `redact_secrets()` 把密钥的**值**替换为 `***`（仅截断是无效的，密钥常出现在开头）。

## 8. 配置查找

`models.yaml` 按以下优先级查找（`load_model_config`）：

1. 显式传入的 `--config` 路径
2. 环境变量 `DIRTIDY_CONFIG`
3. `./models.yaml`
4. `~/.config/dirtidy/models.yaml`

刻意不含「包所在源码树里的 configs/」这类候选：wheel 安装到 `site-packages` 后它必然不存在，
留着只会让报错里出现一条永远为假的路径。示例模板 `configs/models.example.yaml` 作为 package-data
随包分发（`example_config_path()`），安装后依然拿得到。
找不到时报错并列出全部已查找位置，不静默回退到 `models.example.yaml`。
