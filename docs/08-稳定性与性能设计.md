# dirtidy — 稳定性与性能设计

dirtidy 是**单机、单用户的后台程序**（见 `docs/01` §1）：它可以无人值守地长期跑
（`watch` 定时扫描、`desktop` 常驻起服务），也可以被中断后重跑。所以它的稳定性标准
不是交互式工具那一套，而是后台程序那一套：

- **不因单个坏输入整体失败**——一个坏归档、一个没权限的目录不该让整次运行白跑；
- **被中断后不留下损坏或对不上的状态**——尤其不能在「文件已经搬走」和「清单里有记录」之间裂开；
- **长时间运行不无限增长**——缓存、日志、状态目录都要有界；
- **出问题查得到**——审计产物 + `errors.json` + 明确的退出码。

本文写**设计取舍**；内存预算与实测数字见 `docs/07-规模与性能.md`。

### 1.1 产物为什么必须原子写

产物里有 `inventory.json`（可能几百 MB）、`candidates.json`、`quarantine_manifest.json` 等。
原先都是直接 `path.write_text(...)`。后台运行时进程可能被 SIGKILL / OOM 杀掉——
直接写会留下**截断**的 JSON，下一次读取就报「JSON 数组未闭合」。

这比「没有文件」更糟：用户看到的是**数据损坏**，而不是「这次没跑完，重跑一次就行」。
排查方向会被带偏到文件系统上去。

现在 `write_json` / `write_json_stream` / `audit.md` 都走「同目录临时文件 + `os.replace`」。
同目录内的 `os.replace` 在 POSIX 与 Windows 上都是原子的：读者要么看到旧的完整文件，
要么看到新的完整文件。临时文件名带 pid，两个进程也不会互相踩。

> 流式写盘尤其需要这个：5M 条要写几十秒到几分钟，这段时间里被杀的概率比一次性写高得多。

### 1.2 隔离清单为什么写在 `finally` 里

隔离是**破坏性操作**：`shutil.move` 一执行，文件就离开原位了。原先清单在整批搬完之后
才写一次，于是中途被打断就会留下「**文件已离开原位、清单里却查不到**」——
用户不知道它去哪了，也无从还原。这是本工具最不能出的错。

现在清单写入放在 `finally` 里：

```python
try:
    for hit in ordered:
        ...
        shutil.move(str(src), str(dest))
        entries.append(entry)
finally:
    write_json(manifest_path, [e.to_dict() for e in entries])
```

成功路径仍然只写一次（`finally` 在正常退出时也执行）。被打断时，已经搬走的条目
一定在清单里——用户至少知道文件去哪了，`quarantine-restore` 能把它还原回去。

**为什么不是「每搬一条就重写整份清单」**：那是 O(n²)。隔离 10 万条时会把
10 万份清单反复序列化，慢到不可用。要覆盖硬杀场景需要 append-only 日志，
已登记为待办 T-1。

### 1.4 一条容易误解的语义：归档残留对照是「精确字节」

`find_extracted_archives` 拿磁盘文件的 sha256 与归档成员的 sha256 对照，判的是
**解压后字节完全相同**。所以换行符被转换过的文件**不会**被认作归档残留——这是对的：
`a\n` 与 `a\r\n` 确实是两个不同的文件。

但反过来要留意：文本文件在平台之间搬动（或从开了 `core.autocrlf` 的仓库 checkout）之后
字节会变，此前能命中的残留就命不中了。**本仓库自己的 fixture 就踩过这个坑**：
`tests/fixtures/sample_workspace/payload.txt` 必须与同目录 `payload.zip` 里的成员逐字节相同，一旦被转成 CRLF，
size 从 16 变 17 —— 于是它连「待算 hash 的 size 集合」都进不去，`test_archive_hash_candidate`
在 Windows 上必然失败，而 macOS / Linux 默认不转换，一直看不出来。
现在由 `.gitattributes` 固定字节，`test_gitattributes_pins_fixture_bytes` 守着它。

**这不是缺陷，是语义**：本工具从不「猜内容相近」，只报字节级确证。
宁可不报（交人工确认），也不误报一个「看起来一样」的文件。

### 1.5 超时为什么是「协作式」而不是「掐掉」

`watch` 是无人值守的：一轮扫描卡在一块慢盘上，整个监视就静默停住了——
不报错、不退出、也不再有下一轮。这类「看起来还在跑、实际已经不干活了」
比直接崩掉更难发现，所以给它加了单轮时限（`docs/06` T-3）。

**做法上刻意避开了两条看起来更简单的路**：

| 方案 | 为什么不用 |
|------|-----------|
| `signal.alarm` / `SIGALRM` | 只在主线程生效，且只覆盖 Python 层——线程池里算 hash 的那段时间完全不受它约束。而 `watch` 在 Web 侧是**跑在后台线程里的**（界面上的启停），信号根本送不进去 |
| 线程里抛异步异常强杀 | 异步异常可以落在**任意字节码边界**上，包括 `write_json` 写到一半——那正好造出 §1.1 要消灭的那种「截断的产物」 |

所以做成协作式：在扫描与 hash 的循环里埋检查点，到点抛 `RunTimeout`，
并把**已经扫到的部分结果一起带出来**。用户拿到的是「这次跑了一部分」，
而不是「什么都没有」：

- `scan`：已扫到的部分照常跑规则匹配、照常写 run 产物，`meta.timed_out` 标出来，
  `errors.json` 留一条照着能做的提示；退出码 `3`，与「跑失败」区分开。
- `watch`：只跳过这一轮，下一轮照常；**不更新比对基线**——拿只扫了一半的集合去比，
  会把没扫到的全报成「消失」，那是在编数据。

**超时后不执行隔离**。基于「只扫了一半的树」去搬文件，比不搬更糟：
用户看到的是一次「跑完了」的隔离，实际只覆盖了半棵树。待隔离项照常进
`pending_auto_hits.json`，复核后再 `apply-rules`。

默认值两边不一样，理由是使用方式不同：`scan` / `start` 有人盯着，默认不限（0）；
`watch` 无人值守，默认 1800 秒——「一轮卡住等于整个监视停摆」正是 T-3 的触发条件，
所以这里必须给一个默认值，否则那条待办等于没解决。

> 一条容易忽略的细节：超时的 run **看起来和完整产物一模一样**。所以 `meta` 里必须
> 有 `timed_out`，界面上必须有跨分页的警告条——否则用户会把「只扫了半棵树」
> 当成「这个目录里就这么多」。这与审阅页那次「界面看起来做了、实际没做」同源。

## 2. 性能设计

### 2.1 原则：先量再优化，且样本要真

`docs/07` §3.1 记录过一次教训：内存预算模型用 `mtime=1.0`、`suffix=".py"` 这类
**字面量**做样本，字面量被解释器共享，于是每条少算了 mtime 与后缀两份对象，
5M 条的账算少了近一半。这类误差**不会让任何用例变红**，只会在真实数据上以 OOM 出现。

所以这里的规矩是：① 任何性能结论都要有可复现的基准（`scripts/bench_scale.py`）；
② 基准样本必须是真实形态的对象；③ 结论写进 `docs/07` 并注明测法。

### 2.2 三条主线

| 主线 | 目标 | 手段 |
|------|------|------|
| 内存 | 不与 inventory 等长的第二份结构 | `slots`、`_PathIndex`、`select_hashes`、流式写盘/读回、SQLite 缓存 |
| IO | 只读必须读的字节 | **选择性 hash**（见 §2.3）、归档预算早退 |
| 时间 | 不让回调与锁成为瓶颈 | 进度按 1% 节流、hash 走线程池、缓存批量 JOIN |

### 2.3 选择性 hash：只对必要文件算 sha256

原先非 quick 扫描对**所有**文件算 sha256。改成：

```text
要算 hash 的 size 集合 = {size 出现 ≥2 次的文件} ∪ {size 命中某个归档成员的文件}
```

成立依据是两条同 size 的必要性：

- 重复组要求内容相同 ⇒ 必然同 size，所以「size 只出现一次」的文件不可能有重复；
- 归档残留对照要求磁盘文件与成员内容相同 ⇒ 必然同 size，所以磁盘侧只需算
  「size 在成员 size 集合里」的那批。

于是漏算的文件既不可能重复、也不可能与归档成员相同——**结论与全量算完全一致**。
这不是近似，是可证明的等价。

实测（本机合成树，1200 文件）：

```text
scan_tree(full )    3890 条 / 0.51s
pipeline(选择性)    3890 条 / 0.04s   算 hash 521/1320 文件（39.5%），0.02/0.49 MB（5.0%）
```

**文件数只降到 39.5%，字节数却降到 5.0%**——因为会被重复/归档命中的通常是小文件
（缓存、日志、归档成员），而真正占 IO 的大文件基本都只出现一次。对一个后台程序来说，
这是最划算的一刀：省下的主要是 IO 时间，顺带省掉大部分常驻的 sha256 字符串。

代价是选桶本身要一个与文件数同阶的集合（最坏情形 52.4 B/条，5M 约 250 MB，返回后即释放）。
净账见 `docs/07` §3.2。

### 2.4 回归基线

性能结论必须有可复现的入口，否则下次改动只能靠感觉：

```bash
python scripts/bench_scale.py --files 1200    # 条目内存 / 选桶开销 / 扫描吞吐 / inventory 读写
python scripts/smoke_e2e.py                   # 真实目录跑通 scan → apply-rules → analyze
```

改动了扫描、hash、写盘、规则匹配中的任何一处，都应重跑并把新数字更新到 `docs/07` §5。
